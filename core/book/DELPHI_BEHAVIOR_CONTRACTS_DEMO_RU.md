## 1. Три несовпадающих механизма за ключевым словом `array`

В Object Pascal за ключевым словом `array` стоят три принципиально разных механизма с различным размещением в памяти, идентичностью типов и соглашением вызова (ABI). Два из них используют одинаковую запись `array of T`, смысл которой полностью определяется синтаксической позицией ([Structured Types](https://docwiki.embarcadero.com/RADStudio/Florence/en/Structured_Types_(Delphi)), [Parameters](https://docwiki.embarcadero.com/RADStudio/Florence/en/Parameters_(Delphi))):

| Конструкция | Где пишется | Память и дескриптор | Индексы и `SizeOf` | Поведение при `:=` и передаче |
|---|---|---|---|---|
| **Статический массив** (`array[Low..High] of T`) | Объявление типа, поля, переменной | Непрерывный блок значений inline (стек, сегмент данных, запись); заголовка нет | Любой порядковый диапазон `Low..High`; `SizeOf = Count * SizeOf(T)` | Полное копирование всех элементов (по значению) |
| **Динамический массив** (`array of T`) | Объявление типа, поля, переменной | Указатель на `[0]` в куче (`nil` при длине `0`); отрицательно смещённый заголовок `(refCount, length)` | Всегда `0..Length - 1`; `SizeOf(Var) = SizeOf(Pointer)` (`4`/`8` байт) | Разделение одного буфера (`refCount`), **без Copy-on-Write при записи элемента** |
| **Открытый массив** (`array of T`, `array of const`) | **Только** в заголовке формального параметра | На уровне ABI — пара `(PtrToFirst, HighIndex)` без дескриптора кучи | Внутри вызова всегда перенумерован в **`0..High(Param)`** | Зависит от `value` / `const` / `var`; вызов `SetLength` запрещён |

## 2. Синтаксис, номинальная идентичность и ловушка формальных параметров

```pascal
// Фрагмент грамматики массивов и параметров (не полный проект)
type
  TWeekHours = array[1..7] of Integer;             // статический 1-индексный массив
  TGrid2x3   = array[0..1, 0..2] of Double;        // прямоугольный статический блок
  TNumbers   = array of Integer;                   // именованный динамический массив
  TJagged    = array of array of Integer;          // зубчатый динамический массив

procedure UseDynamic(const A: TNumbers);           // принимает ТОЛЬКО TNumbers (или nil)
procedure UseOpen(const A: array of Integer);      // открытый массив: примет TWeekHours, TNumbers, [1, 2], Slice(...)
procedure UseVarArgs(const Args: array of const);  // вариантный открытый массив (array of TVarRec)
```

**Две критические границы типизации:**
1. **`P(A: TNumbers)` не равен `P(A: array of Integer)`:** первый параметр требует конкретный динамический тип `TNumbers` (допускает `nil`, а без `const` передаёт дескриптор с увеличением `refCount` без копирования элементов); второй — открытый массив, принимающий любой однотипный статический или динамический массив, срез `Slice(Arr, Count)` и конструктор `[10, 20]`, перенумеровывая индексы внутри тела процедуры в `0..High(A)`.
2. **Несовместимость анонимных массивов для `var`/`out`:** две отдельные декларации `var A: array[0..3] of Integer;` и `var B: array[0..3] of Integer;` создают разные анонимные типы, несовместимые с именованным `var`-параметром (`E2033`). Для передачи по ссылке всегда объявляют общий именованный тип в секции `type`.

## 3. Память динамических массивов, отсутствие COW, глубина `Copy` и открытые параметры

### Дескриптор кучи, алиасинг и `SetLength`

По правилам [Internal Data Formats](https://docwiki.embarcadero.com/RADStudio/Florence/en/Internal_Data_Formats_(Delphi)) переменная динамического массива занимает `4` байта на 32-битных и `8` байт на 64-битных платформах (`nil` соответствует пустому массиву длины `0`). Перед элементом `[0]` в куче лежит заголовок со счётчиком ссылок `refCount` и длиной `length` (расширенной до разрядности платформы на 64-bit):
- **Нет Copy-on-Write на элементах:** присваивание `B := A` увеличивает `refCount`, после чего запись `B[0] := 9` **немедленно меняет `A[0]`**, поскольку обе переменные смотрят в один буфер!
- **Уникализация через `SetLength` ([System.SetLength](https://docwiki.embarcadero.com/Libraries/Florence/en/System.SetLength)):** вызов `SetLength(B, NewLen)` — в том числе `SetLength(B, Length(B))` с прежней длиной — гарантирует `refCount = 1`: если буфер разделялся (`refCount > 1`), выделяется новый блок и элементы копируются, изолируя `B` от `A` (подтверждено примером 01 (`../../../examples/01-array-alias.dpr`), `OBSERVED_PASS` на Delphi 13 Win32 Debug: вывод `9`, `9`, `12`). Новые ячейки при расширении обнуляются (`Default(T)`), отброшенные при усечении — финализируются.

### Поверхностность `Copy` и многомерные массивы

- **`Copy(A)` / `Copy(A, Index, Count)`:** создаёт новый внешний динамический массив, но выполняет **поверхностное (shallow) копирование** элементов. Если элементы — ссылки на экземпляры `class`, интерфейсы или вложенные динамические массивы (`TJagged`), внутренние строки и объекты остаются общими между `A` и копией!
- **Прямоугольные против зубчатых (jagged) массивов:** статический `array[0..1, 0..2] of Double` — единый непрерывный блок в памяти (по строкам, row-major); динамический `array of array of Integer` — массив указателей на независимые одномерные массивы в куче, где каждая строка может иметь собственную длину или быть `nil`.

### Операции динамических массивов (XE7+): `Insert`, `Delete`, `Concat`, оператор `+`, `Copy` и aliasing vs detachment

Начиная с ветки **Delphi XE7+**, динамические массивы получили встроенную алгебру конкатенации и структурной модификации без ручных циклов `Move` и `SetLength`. В двухархитектурных пробах **`P15_DynArray_Ops32`** (`Win32`, `pe=0x14c`, `0` диагностик, `run_exit = 0`) и **`P15_DynArray_Ops64`** (`Win64`, `pe=0x8664`, `0` диагностик, `run_exit = 0`) проверены все операции и точная граница между разделением буфера (*aliasing*) и отцеплением копии (*detachment*):

```pascal
// Иллюстративный фрагмент (проверено в P15_DynArray_Ops32 / P15_DynArray_Ops64)
A := [1, 2, 3];
B := [4, 5];
C := A + B;                  // C_plus=[1,2,3,4,5]
D := Concat(A, B, [6]);      // D_concat=[1,2,3,4,5,6]
Insert(99, C, 1);            // C_ins1=[1,99,2,3,4,5] — вставка одного элемента по 0-индексу
Insert([77, 88], C, 0);      // C_ins_sub=[77,88,1,99,2,3,4,5] — вставка подмассива
Delete(C, 2, 2);             // C_del=[77,88,2,3,4,5] — удаление 2 элементов с индекса 2
E := Copy(C, 1, 3);          // E_copy=[88,2,3] — срез 3 элементов с индекса 1
```

| Операция над алиасом (`Alias* := A`, где `A = [10, 2, 3]`, `refCount > 1`) | Меняет ли исходный `A`? | Измеренный `stdout` в `P15_DynArray_Ops32` / `64` |
|---|---|---|
| Поэлементная запись `Alias[0] := 10` (на исходном `[1, 2, 3]`) | **Да** (пишет в общий буфер) | `A_after_alias=[10,2,3]` |
| Вставка `Insert(55, Alias2, 0)` | **Нет** (отцепляет новую копию) | `A_after_insert=[10,2,3];Alias2=[55,10,2,3]` |
| Удаление `Delete(Alias3, 0, 1)` | **Нет** (отцепляет новую копию) | `A_after_delete=[10,2,3];Alias3=[2,3]` |
| Изменение длины `SetLength(Alias4, 5)` | **Нет** (отцепляет новую копию) | `A_after_setlength=[10,2,3];Alias4_len=5` |

Принципиальный вывод из этих проб: индексированная запись `Alias[I] := X` изменяет разделяемый буфер на месте. В проверенных структурно-размерных вызовах (`Insert`, `Delete`, `SetLength`) при `refCount > 1` уникализируется буфер целевой переменной (*detachment*); другие переменные продолжают ссылаться на прежний буфер. Эти наблюдения не устанавливают поведение для всех аргументов, включая операции без эффекта.

### Стоимость и ограничения открытых массивов (`value` / `const` / `var`)

- **Открытый массив по значению (`procedure P(A: array of Integer)`):** при входе в процедуру компилятор выделяет локальный буфер и **копирует все элементы** переданной последовательности (освобождая копию на выходе); для крупных массивов это создаёт скрытые накладные расходы (при этом объекты внутри элементов по-прежнему не клонируются).
- **По `const` (`const A: array of Integer`):** копия элементов не создаётся — передаётся только пара `(Ptr, High)`, а запись в `A[i]` запрещена компилятором (но не защищена от изменения через внешний алиас).
- **По `var` (`var A: array of Integer`):** мутирует исходный массив вызывающего напрямую; передача временного конструктора `[1, 2]` в `var`-параметр запрещена и отвергается с ошибкой `E2197` (подтверждено отрицательной парой 06 (`../../../examples/README.md`) на Delphi 13 Win32 Debug).

## 4. `array of const` и физика `TVarRec`

Конструкция `array of const` допустима только в списке формальных параметров и эквивалентна открытому массиву `array of System.TVarRec`. Она позволяет передать разнородный список значений (`Format('%d: %s', [42, Title])`) без создания тяжёлых `Variant`:

- Каждому элементу на стеке вызывающей стороны строится запись `TVarRec`, содержащая 1-байтовый тег `VType` (`vtInteger`, `vtBoolean`, `vtChar`, `vtExtended`, `vtString`, `vtPointer`, `vtPChar`, `vtObject`, `vtClass`, `vtWideChar`, `vtPWideChar`, `vtAnsiString`, `vtCurrency`, `vtVariant`, `vtInterface`, `vtInt64`, `vtUnicodeString`) и поле значения/указателя (8 байт для встроенных скалярных ветвей / ширина указателя на 64-bit).
- **Критическая ловушка времени жизни `TVarRec`:** `TVarRec` — **неуправляемая** вариантная структура! Поля `VUnicodeString`, `VAnsiString`, `VInterface` хранятся в ней как сырые `Pointer` без увеличения `refCount`, а `VExtended`, `VInt64`, `VCurrency`, `VVariant` указывают на временные стековые слоты в кадре вызывающей функции. Сохранять запись `TVarRec` или взятые из неё сырые указатели за пределы вызова категорически нельзя — после возврата из процедуры они становятся висячими!

## 1. Два уровня управляемости записей: от автополей к CMR

В модели памяти Delphi ([Memory Management](https://docwiki.embarcadero.com/RADStudio/Florence/en/Memory_Management), [Custom Managed Records](https://docwiki.embarcadero.com/RADStudio/Florence/en/Custom_Managed_Records)) время жизни записи (`record`) управляется компилятором на двух уровнях:

1. **Автоуправляемая запись (запись со встроенными managed-полями):** как только обычная `record` включает хотя бы одно поле типа `string`, динамического массива, `IInterface`, `Variant` или вложенной управляемой записи, компилятор формирует для неё RTTI-таблицу смещений управляемых полей и автоматически вставляет вызовы RTL-процедур (`_InitializeRecord`, `_FinalizeRecord`, `_CopyRecord`), оборачивая область жизни переменной в скрытый блок `try ... finally`.
2. **Custom Managed Records (CMR, введены в Delphi 10.4 Sydney):** позволяют разработчику объявить собственные перехватчики жизненного цикла — `class operator Initialize`, `Finalize` и `Assign`. Это превращает запись в детерминированный контейнер времени жизни (для дескрипторов ОС, не-управляемых буферов, блокировок, журналов состояния), встраиваемый прямо в кодогенерацию прологов, эпилогов, массивов и раскрутки исключений.

## 2. Синтаксис операторов: классическая форма 10.4+ и неявный `Self` в Delphi 13

### Полные сигнатуры (Delphi 10.4 Sydney+)

```pascal
// Фрагмент объявления CMR в стиле 10.4+ (проверенные проекты — examples/19, 37, 39, 47)
type
  TManagedResource = record
  strict private
    FRawHandle: Pointer;
  public
    class operator Initialize(out Dest: TManagedResource);
    class operator Finalize(var Dest: TManagedResource);
    class operator Assign(var Dest: TManagedResource; const [ref] Src: TManagedResource);
  end;
```

Требования компилятора к сигнатурам строги:
- **`Initialize(out Dest: TRec)`:** обязан принимать ровно один параметр `out` типа самой записи. Модификатор `out` подчёркивает, что на входе скалярные поля `Dest` содержат **неинициализированные байты стека/кучи** (вложенные автоуправляемые поля при этом обнуляются компилятором до входа в пользовательский код).
- **`Finalize(var Dest: TRec)`:** принимает один параметр `var` типа записи; вызывается при выходе из области видимости, раскрутке исключения, уничтожении внешнего объекта/массива или в `finalization` модуля.
- **`Assign(var Dest: TRec; const [ref] Src: TRec)`:** перехватывает копирование `Dest := Src` (в отличие от операторов приведения типов `Implicit`/`Explicit`, рассмотренных в главе 33 (`33-operators.md`)). Второй параметр обязан иметь квалификатор **`const [ref]`**, иначе передача `Src` по значению породила бы бесконечную рекурсию вызова `Assign`!

### Сокращённый синтаксис с неявным `Self` (Delphi 13 Florence+)

Начиная с **Delphi 13.0 Florence** ([What's New](https://docwiki.embarcadero.com/RADStudio/Florence/en/What%27s_New)), в объявлениях `Initialize` и `Finalize` разрешено опускать формальный параметр `Dest` — внутри тела оператора экземпляр записи доступен через неявный `Self`:

```pascal
// Синтаксис Delphi 13+ (полный проверенный проект — examples/38-managed-implicit-self.dpr)
type
  TObserved = record
    Value: Integer;
    class operator Initialize;
    class operator Finalize;
  end;
```

Сокращённая форма подтверждена примером 38 (`../../../examples/README.md`) (`OBSERVED_PASS` на Delphi 13 Win32 Debug: `7`, `final`, `end`), а полная форма 10.4+ остаётся полностью рабочей (примеры 19, 37, 39, 47 (`../../../examples/README.md`)) и обязательна, если код должен компилироваться в Delphi 10.4–12.

## 3. Скрытые точки вызова, инварианты `Assign` и передача параметров

### Где компилятор вызывает операторы CMR и почему нельзя считать копии

- **Локальная `var` против `inline var`:** обычная локальная переменная инициализируется в прологе подпрограммы и финализируется при выходе из неё (пример 19 (`../../../examples/19-managed-record.dpr`), `OBSERVED_PASS`: `5`, `1`); блочная `inline var R: TRec` инициализируется в точке объявления внутри вложенного `begin ... end` и финализируется на выходе из этого блока (глава 16 (`16-variables.md`)).
- **Массивы, объекты и куча:** при создании класса или расширении массива `SetLength` для каждого элемента вызывается `Initialize`, при уничтожении/сжатии — `Finalize` (если при инициализации массива на `K`-м элементе возникнет исключение, финализированы будут только уже успешно созданные элементы `0..K-1`). Для ручной кучи `New(P)` и `Dispose(P)` автоматически вызывают `Initialize`/`Finalize`, тогда как сырые `GetMem`/`FreeMem` их **игнорируют** и требуют явных [System.Initialize](https://docwiki.embarcadero.com/Libraries/Florence/en/System.Initialize) / `System.Finalize` (глава 14 (`14-pointers.md`)).
- **Запрет опоры на точное число копий:** возврат функции через `Result`, передача временных выражений и оптимизации (copy elision) могут менять количество вызовов `Initialize`/`Assign`/`Finalize` между версиями и платформами. Логика владения обязана опираться на корректный подсчёт ссылок или передачу владения, а не на ожидание фиксированного счётчика вызовов.

### Две обязательные защиты внутри `Assign`

На входе в `Assign(var Dest; const [ref] Src)` переменная `Dest` **уже инициализирована** и может владеть активным ресурсом. Поэтому любая ресурсная реализация `Assign` обязана:
1. **Защититься от самоприсваивания (`A := A`):** первой строкой проверить `if @Dest = @Src then Exit;` (иначе освобождение старого ресурса `Dest` уничтожит источник `Src`!). В примере 39 (`../../../examples/README.md`) (`OBSERVED_PASS`: `9`, `9`) показана эта адресная проверка на скалярном поле, но для реального дескриптора или буфера к ней добавляется второй шаг;
2. **Освободить прежний ресурс `Dest`** (или уменьшить его счётчик ссылок) перед записью нового ресурса из `Src`, иначе прежний дескриптор утечёт.

### Матрица передачи параметров (подтверждена примером 47 (`../../../examples/README.md`))

| Объявление параметра | Поведение времени жизни и копирования |
|---|---|
| `ByValue(R: TRec)` | Создаётся отдельная локальная копия (`Initialize` + `Assign` или копирование), финализируемая при выходе из `ByValue`; оригинал вызывающего не меняется |
| `ByVar(var R: TRec)` | Передаётся прямая ссылка на существующий экземпляр без `Initialize`/`Assign`/`Finalize` |
| `ByConstRef(const [ref] R: TRec)` | Гарантирует передачу по ссылке для чтения без создания временной копии и без вызова `Assign` |
| `ByConst(const R: TRec)` | В примерах документации CMR передаётся без копии, но в общем ABI `const` без `[ref]` зависит от размера/платформы — для предсказуемого отсутствия копирования у CMR предпочтителен `const [ref]` |

## 4. Критический контракт отказа: исключение внутри `Initialize`

По официальному контракту [Custom Managed Records](https://docwiki.embarcadero.com/RADStudio/Florence/en/Custom_Managed_Records), подтверждённому живым прогоном примера 37 (`../../../examples/README.md`) (`OBSERVED_PASS` на Delphi 13 Win32 Debug: вывод `caught` и `FinalizeCount = 0`):

> **Если пользовательский `class operator Initialize` выбрасывает исключение, парный `class operator Finalize` для этой записи НЕ вызывается!**

Это принципиально отличает CMR от двух других механизмов очистки в языке (глава 68 (`68-lifetime-boundaries.md`)):
- у **`class`:** исключение в `constructor Create` **автоматически вызывает** `destructor Destroy` на частично сконструированном экземпляре;
- у **`unit`:** исключение в секции `initialization` останавливает запуск, а для уже прошедших инициализацию модулей выполняется штатная `finalization` по контракту главы 01 (`01-project.md`) (если не вызван `System.Halt`);
- у **CMR (`record`):** не завершившая `Initialize` запись считается несуществующей, поэтому частичный захват ресурсов внутри `Initialize` (например, первый дескриптор открыт, а второй вызвал сбой) **обязан откатываться локально внутри `try ... except` самого `Initialize`**!

Обратная сторона: выбрасывать необработанное исключение из `Finalize` во время раскрутки другого исключения недопустимо, так как оно перекроет исходную ошибку.

## 5. Границы C++ (`.hpp`) и обобщений (`RECORD_CONSTRAINT_MANAGED_BOUNDARY`)

- **Неподдержанное время жизни в C++ consumer:** по прямому предупреждению [Custom Managed Records](https://docwiki.embarcadero.com/RADStudio/Florence/en/Custom_Managed_Records) CMR **не поддерживаются в C++** как автоматически управляемые типы: сгенерированный `.hpp` не создаёт полноценных конструкторов/деструкторов/операторов копирования C++. Успешная сборка заголовка не означает сохранения RAII на стороне C++ (глава 65 (`65-cpp-header-contracts.md`)).

Обобщения (*generics*, введены в **Delphi 2009**, [Declaring Generics](https://docwiki.embarcadero.com/RADStudio/Florence/en/Declaring_Generics)) позволяют параметризовать классы, записи, интерфейсы, динамические массивы, процедурные типы и методы формальными параметрами типа. Внутри собственного объявления `TBox<T>` выступает как **открытая форма**, а после подстановки конкретного типа (`TBox<Integer>`, `TBox<string>`) порождает **закрытую специализацию** (*constructed type*) со своей физической раскладкой и собственными классовыми данными.

## Физика специализаций против стирания типов и шаблонов C++

Обобщения в Delphi принципиально отличаются как от модели стирания типов в Java (*type erasure*), так и от текстово-утиной инстанциации шаблонов в C++:

1. **Проверка тела в точке объявления (против C++ `template`).** Компилятор проверяет открытое тело `TBox<T>` один раз против объявленных ограничений (глава 32 (`32-constraints.md`)). Без ограничений `T` трактуется как непрозрачное значение: его можно хранить, копировать через `:=`, передавать и возвращать, но нельзя вызывать `T.Create`, складывать `A + B`, сравнивать `A = B` или обращаться к неподтверждённым членам.
2. **Настоящие раздельные типы в бинарном коде (против Java).** Каждая закрытая специализация получает собственное представление времени выполнения:
   - **Раскладка памяти:** поле `Value: T` занимает ровно `SizeOf(T)` байт с выравниванием `T`, поэтому `TBox<Byte>` и `TBox<Int64>` имеют разный `InstanceSize`.
   - **Таблица управляемых полей:** если аргумент `T` управляемый (`string`, `IInterface`, динамический массив, CMR), данная специализация получает собственную `vmtInitTable`, автоматически зануляющую и финализирующую поле `Value` (глава 35 (`35-memory.md`)).
   - **Раздельные `class var`:** у каждой закрытой специализации выделяется **собственная независимая ячейка статических данных** ([Class Variable in Generics](https://docwiki.embarcadero.com/RADStudio/Florence/en/Class_Variable_in_Generics)). За счёт кодогенерации для каждой специализации большое число закрытых инстанциаций увеличивает объём `.dcu` и исполняемого файла.

### Compile-time intrinsics оптимизации специализаций: `GetTypeKind(T)`, `IsManagedType(T)`, `HasWeakRef(T)`

Внутри тела обобщённого типа или метода доступны выражения этапа компиляции `SizeOf(T)`, `Default(T)`, `TypeInfo(T)`, а начиная с **Delphi XE7** — компиляторные интринсики `GetTypeKind(T)`, `IsManagedType(T)` и `HasWeakRef(T)`. Поскольку в каждой закрытой специализации их результат константен, ветки вида `if IsManagedType(T) then ...` сворачиваются на этапе компиляции без накладных расходов перехода во время выполнения. Выражение `Default(T)` возвращает нулевое значение типа (`0`, `False`, `nil`, `''`, обнулённую запись), а присваивание `Value := Default(T)` для управляемого `T` штатно освобождает прежний строковый буфер или интерфейс.

В сериях живых проб **`P15_Intrinsics_TypeMeta32_V2` / `64_V2`** (`Win32` `0x14c` и `Win64` `0x8664`, `0` диагностик, `exit=0`) и **`P15_HasWeakRef_*`** (`Win32` Debug, `0` диагностик) измерены выбранные типы. Колонка `System.HasWeakRef` ниже исправлена отдельными пробами редакции 1.2.0; старое обобщение диагностики `E2571` снято:

| Проверяемый тип `T` | `GetTypeKind(T)` | `IsManagedType(T)` | `System.HasWeakRef(T)` *(P15 и отдельные пробы 1.2.0)* | Физический смысл и граница |
|---|---|---|---|---|
| `Integer`, `Double`, `Pointer` | `tkInteger`, `tkFloat`, `tkPointer` | `False` | `False` (1.2.0, обе архитектуры) | Скаляры и сырые указатели без скрытой финализации |
| `ShortString` | `tkString` | **`False`** | `False` (1.2.0, обе архитектуры) | Встроенный строковый тип с байтом длины (`string[1..255]`) без кучи |
| `AnsiString`, `string` (`UnicodeString`), `WideString` | `tkLString`, `tkUString`, `tkWString` | **`True`** | `False` (1.2.0, обе архитектуры) | Управляемые строковые буферы (`RefCount` / COM BSTR) |
| `TBytes` (`array of Byte`) | `tkDynArray` | **`True`** | `False` (1.2.0, обе архитектуры) | Динамический массив со счётчиком ссылок |

| **`TUnsafeIntfRec` (`record [unsafe] F: IInterface; end`)** | `tkRecord` | **`False`** | **`False`** (`_RecWeak32`) | Атрибут `[unsafe]` полностью снимает подсчёт ссылок и признак managed |
| `TObject` / `THolder = class [weak] W: IInterface; end` | `tkClass` | `False` | **`False`** (`_ClassIntf32`, `_GenClass32`) | На классическом non-ARC Windows экземпляры классов управляются вручную |

**Разрешение имени и проверенная область `HasWeakRef`:**

1. [Встроенная операция `System.HasWeakRef`](https://docwiki.embarcadero.com/Libraries/Florence/en/System.HasWeakRef) принимает **имя типа**. Одноимённая [функция `System.TypInfo.HasWeakRef`](https://docwiki.embarcadero.com/Libraries/Florence/en/System.TypInfo.HasWeakRef) принимает **`PTypeInfo`**. Это разные операции. После `uses System.TypInfo` пишите `System.HasWeakRef(T)` либо `System.TypInfo.HasWeakRef(TypeInfo(T))` явно. В пробах `QualifiedHasWeakRef_Win32/64` оба способа дали `True` для записи со слабым интерфейсным полем и `False` для простой записи; неквалифицированный вызов с именем типа не скомпилировался.
2. **Запрет скаляров и неограниченного `<T>` не подтверждается.** `ConcreteHasWeakRef_Win32/64` принимает `Integer`, `Double`, `ShortString`, `AnsiString`, `string`, `WideString`, `TBytes`, `Pointer`, `Variant` и возвращает `False`. `GenericWeakRefRun_Win32/64` принимает `TBox<T>` без ограничения: специализации с `Integer`, `string`, простой записью дают `False`, со слабой записью — `True`. Все эти программы выполнены с `exit=0` на Delphi 13 CE `37.0.60542.8024`, Debug.
3. Исторические `P15_Intrinsics_TypeMeta32/64` записывали `E2571`, но при повторной сборке опубликованного исходника наблюдалась коллизия с функцией из `System.TypInfo` и другие диагностики. Текст исходника не содержит прежнего вызова в описанном месте. Старые квитанции сохранены, но они **не являются доказательством общего ограничения intrinsic**. Ограниченные `T: class` и `T: record` из отдельных P15-проб также остаются допустимыми в измеренном профиле.

Новая квитанция 1.2.0 (`../../../evidence/compiler/demo-sample-receipts.json`) фиксирует исходники и их зависимости. Наблюдение Windows не назначает результаты старым или мобильным компиляторам.

## Формальная грамматика и ограничения объявлений

```pascal
// Синтаксический срез допустимых обобщённых конструкций (не полный проект)
type
  TBox<T> = class
    Value: T;
  end;
  TPair<TKey, TValue> = record
    Key: TKey;
    Value: TValue;
  end;
  IReader<T> = interface
    function Read: T;
  end;
  TItems<T> = array of T;                     // Обобщённый динамический массив (НЕ открытый массив!)
  THandler<T> = procedure(const Value: T);    // Обобщённый процедурный тип

  TIdentity = class
    class function Keep<T>(const Value: T): T; static; // Обобщённый метод внутри класса/записи
  end;
```

Пять строгих синтаксических правил:
1. **Запрет свободных (top-level) generic-подпрограмм.** В отличие от C++ и C# local functions, на уровне модуля в Delphi нельзя объявить свободную `function Max<T>(const A, B: T): T;` — обобщённые подпрограммы оформляются **только как методы класса или записи** (пример 10 (`../../../examples/README.md`), `OBSERVED_PASS`: `TIdentity.Keep<Integer>(42)` выводит `42`). В заголовке реализации список параметров типа повторяется (`class function TIdentity.Keep<T>(const Value: T): T;`), но без повторной записи ограничений `: record` / `: class`.
2. **Запрет полиморфных generic-методов (`E2533`).** Конструкторы, деструкторы, а также `virtual`, `dynamic` и `message`-методы не могут объявлять собственный список параметров типа `<U>` (фиксированная таблица слотов VMT класса не может вместить заранее неизвестное множество будущих специализаций метода).
3. **Область видимости параметра типа и предок.** Параметр `T` из `TBox<T>` не наследуется автоматически как имя в заголовке потомка: пишут `TChild<S> = class(TBox<S>)`. Предком класса может быть обычный класс или специализированный generic-класс (`class(TBox<Integer>)`, `class(TBox<S>)`), но **не** голый параметр типа (`class(T)` запрещён).
4. **Псевдонимы специализаций.** Объявление `type TIntCounter = TCounter<Integer>;` обозначает ту же самую специализацию, а не новый отдельный тип.
5. **Отсутствие частичной специализации и нетиповых параметров.** В отличие от C++ (`template<typename T, int N>`), параметры в `<...>` всегда обозначают только типы, а явная перегрузка тела шаблона под один конкретный тип не поддерживается.

## 1. Классификация, синтаксис запятых и перегрузка коротких букв

Директивы компилятора в Embarcadero Delphi записываются внутри комментариев `{$...}` или `(*$...*)`, где символ `$` обязан следовать **непосредственно** за открывающей скобкой без пробела (запись `{ $R+}` — обычный комментарий, который компилятор молча пропускает). По своей природе все директивы делятся на три семейства ([Compiler Directives List](https://docwiki.embarcadero.com/RADStudio/Florence/en/Delphi_Compiler_Directives_(List)_Index), [Delphi compiler directives](https://docwiki.embarcadero.com/RADStudio/Florence/en/Delphi_compiler_directives)):

1. **Переключатели (`Switch directives`):** имеют однобуквенную форму `{$R+}` / `{$R-}` и длинную форму `{$RANGECHECKS ON}` / `{$RANGECHECKS OFF}`.
   - **Правило запятой (пример 45 (`../../../examples/README.md`), `OBSERVED_PASS`):** однобуквенные переключатели разрешено группировать через запятую без пробелов (`{$B+,R-}`), тогда как в длинной форме текст после первого переключателя и пробела/запятой трактуется как хвостовой комментарий и **не включает** вторую директиву! Поэтому длинные директивы всегда пишут раздельными блоками `{$BOOLEVAL ON}{$RANGECHECKS OFF}`.
2. **Параметрические директивы (`Parameter directives`):** передают компилятору или компоновщику имя файла, число, идентификатор или фильтр (`{$ALIGN 8}`, `{$MINENUMSIZE 4}`, `{$APPTYPE CONSOLE}`, `{$WARN SYMBOL_DEPRECATED ERROR}`, `{$RTTI EXPLICIT ...}`).
3. **Условные директивы (`Conditional directives`):** управляют отбором исходного текста до синтаксического анализа (`{$DEFINE}`, `{$UNDEF}`, `{$IFDEF}`, `{$IFNDEF}`, `{$IF}`, `{$ELSEIF}`, `{$ELSE}`, `{$ENDIF}`, `{$IFEND}`, `{$IFOPT}` — см. главу 42 (`42-conditionals.md`)).

### Коллизии однобуквенных форм

Одна и та же буква в короткой записи исторически обслуживает совершенно разные механизмы в зависимости от аргумента:

| Буква | Переключатель (`+` / `-`) | Параметрическая / иная форма |
|---|---|---|
| `$R` | `{$R+}` / `{$R-}` — проверка границ диапазонов (`RANGECHECKS`) | `{$R file.res [Pred]}` — линковка файла ресурсов (`RESOURCE`) |
| `$I` | `{$I+}` / `{$I-}` — генерация проверок файлового ввода-вывода (`IOCHECKS`) | `{$I file.inc}` — лексическая вставка исходного текста (`INCLUDE`) |
| `$M` | `{$M+}` / `{$M-}` — классическая RTTI для секции `published` (`TYPEINFO`) | `{$M minstack,maxstack}` — размеры стека исполняемого образа (`MINSTACKSIZE`/`MAXSTACKSIZE`) |
| `$A` | `{$A+}` / `{$A-}` — выравнивание полей по умолчанию / без выравнивания | `{$A1}`, `{$A2}`, `{$A4}`, `{$A8}`, `{$A16}` — явный шаг `ALIGN` |
| `$D` | `{$D+}` / `{$D-}` — номера строк для отладчика (`DEBUGINFO`) | `{$D 'text'}` — строка описания модуля (`DESCRIPTION`); `{$D0..D2}` — см. главу 71 (`71-compilation-layers.md`) |
| `$L` | `{$L+}` / `{$L-}` — таблица локальных символов (`LOCALSYMBOLS`) | `{$L file.obj}` — подключение внешнего объектного модуля (`LINK`) |

## 2. Четыре области действия и изменения современных версий (`PUSHOPT` / `IFOPT`)

Помимо деления на `Global` (на весь модуль, до `interface`/`uses`) и `Local` (от точки встречи вниз по тексту), критично различать:
- **Гранулярность целой подпрограммы:** опции вроде `{$OPTIMIZATION}` (`{$O}`) и `{$STACKFRAMES}` (`{$W}`) применяются к процедуре целиком, а не к одной строке внутри `begin..end`.
- **Запекание в объявление типа:** `{$ALIGN}`, `{$MINENUMSIZE}`, `{$SCOPEDENUMS}`, а также свойство масштабируемой адресной арифметики типизированного указателя (карточка указательной арифметики (`../directives/pointermath.md`), пример 26 (`../../../examples/README.md`)) запоминаются самим типом в точке `type T = ...;`.
- **Лексические директивы литералов (Delphi 12+):** управление форматом переводов строк многострочных литералов `'''` (`CRLF` против `LF`, карточка многострочных литералов (`../directives/textblock.md`), пример 28 (`../../../examples/README.md`) и живая проба `P7_TextBlock_CRLF_LF` с длиной `12` против `11` и автоснятием отступа закрывающих `'''`).

В **Delphi 13 Florence** стек опций и проверка состояния получили ключевые обновления ([What's New](https://docwiki.embarcadero.com/RADStudio/Florence/en/What%27s_New), [Option OPT](https://docwiki.embarcadero.com/RADStudio/Florence/en/Option_OPT_(Delphi)), [IFOPT](https://docwiki.embarcadero.com/RADStudio/Florence/en/IFOPT_directive_(Delphi))):
- **`{$PUSHOPT}` и `{$POPOPT}`** (карточка PUSHOPT (`../directives/pushopt-popopt.md`), пример 29 (`../../../examples/README.md`), `OBSERVED_PASS`: `on`, `off`, `on`) сохраняют и восстанавливают состояние поддерживаемых опций компилятора без ручного ветвления;
- **`{$IFOPT}` с длинными именами** (пример 44 (`../../../examples/README.md`), `OBSERVED_PASS`: `scoped`, `flat`) позволяет проверять переключатели без короткого однобуквенного кода, например `{$IFOPT SCOPEDENUMS ON}`.

## 1. Почему одного имени `Extended` недостаточно

В исходном тексте на Object Pascal тип `System.Extended` записывается одинаково на любой платформе, однако на уровне бинарного представления и машинных регистров он распадается на разные профили. По таблицам [System.Extended](https://docwiki.embarcadero.com/Libraries/Florence/en/System.Extended) и [Multi-Device Considerations](https://docwiki.embarcadero.com/RADStudio/Florence/en/Delphi_Considerations_for_Multi-Device_Applications):

| Целевая платформа (CPU / OS) | `SizeOf(Extended)` | Аппаратное устройство и существенная граница |
|---|---|---|
| Intel Win32 (x86) | **10 байт** | Аппаратный 80-битный формат x87 FPU (1 бит знака + 15 бит экспоненты + **явный** целый бит + 63 бита дроби) |
| Intel Win64 (x64, при `{$EXTENDEDCOMPATIBILITY OFF}`) | **8 байт** | Псевдоним IEEE `Double` (`binary64`, 53 бита значимой мантиссы на регистрах SSE2 `XMM`) |
| Intel Linux64 / Intel macOS64 | **16 байт** | 80-битное значение x87 с 6 байтами выравнивания по ABI System V (**не** IEEE `binary128`!) |
| ARM (Android, iOS, macOS ARM64) | **8 байт** | Псевдоним IEEE `Double` (включая Apple Silicon ARM64; не путать со старым примером macOS Intel без указания CPU) |

## 2. Совместимость хранения (`{$EXTENDEDCOMPATIBILITY}`, `TExtended80Rec`) и `EXTENDED_TARGET_PROFILE` (`../SOURCE_ISSUES.md#issue-extended-target-profile`)

При переносе бинарных файлов и записей между Win32 и 64-битными таргетами необходимо строго разделять **размер буфера хранения** и **разрядность самой арифметики**:

- **`{$EXTENDEDCOMPATIBILITY ON|OFF}` (карточка EXTENDEDCOMPATIBILITY (`../directives/extendedcompatibility.md`), default `OFF`):** локальная директива на странице [Extended type compatibility](https://docwiki.embarcadero.com/RADStudio/Florence/en/Extended_type_compatibility_(Delphi)) переключает `Extended` в 10-байтовый формат хранения ради двоичной совместимости структур. Однако на Win64 это **не включает 80-битную арифметику x87**: вычисления выполняются в 53-битной мантиссе `Double` на SSE2!
- **`System.TExtended80Rec` ([TExtended80Rec](https://docwiki.embarcadero.com/Libraries/Florence/en/System.TExtended80Rec)):** упакованная 10-байтовая запись (`Words`, `Bytes`, `Frac`, `Exp`, `Sign`), явно отделяющая сериализацию 80-битных потоков данных от арифметического типа текущей платформы.

### Решающие измерения серии P13 (`P13_ExtCompat_Prec_On32/64` и `P13_ExtPrecision_Off32/64`, `OPEN` для не-Windows)

В серии **P13** на `Delphi 13 CE` (`37.0.60542.8024`, `Win32` `0x14c` и `Win64` `0x8664`, Debug, `0` диагностик; наряду с примером 50 (`../../../examples/README.md`)) одновременно измерены `SizeOf`, смещения полей в `TUnpacked = record A: Byte; E: Extended; B: Byte; end` и `TPacked = packed record A: Byte; E: Extended; B: Byte; end`, тест 64-битной мантиссы `prec64 = ((1.0 + 1e-17) <> 1.0)` и побайтовый `round-trip` `Extended -> TExtended80Rec -> Extended`:

| Режим и таргет | `SizeOf(Extended)` / `TExtended80Rec` | `TUnpacked` (`SizeOf; offE; offB`) | `TPacked` (`SizeOf; offE; offB`) | `prec64` (`1 + 1e-17 <> 1`) | Побайтовый `round-trip` (`rt_eq`) |
|---|---|---|---|---|---|
| **Win32** `OFF` и **`ON`** (`P13_ExtCompat_Prec_On32`) | `10` / `10` | `24; offE=8; offB=18` | `12; offE=1; offB=11` | **`TRUE`** (x87 64-бит мантисса) | **`TRUE`** (`0AC264DA3FE0E9F60540`) |
| **Win64** `OFF` (`P13_ExtPrecision_Off64`) | `8` / `10` | `24; offE=8; offB=16` | `10; offE=1; offB=9` | **`FALSE`** (SSE2 `Double`) | `TRUE` (`984CFB073CDD5E40` — уже 8-байтный `Double`) |
| **Win64** **`{$EXTENDEDCOMPATIBILITY ON}`** (`P13_ExtCompat_Prec_On64`) | **`10` / `10`** | **`24; offE=8; offB=18`** | **`12; offE=1; offB=11`** | **`FALSE`** (арифметика всё ещё `Double`!) | **`FALSE`!** (10 байт `0AC264DA3FE0E9F60540` усекаются через `Double`!) |

**Ключевой физический вывод:** на `Win64` директива `{$EXTENDEDCOMPATIBILITY ON}` точно восстанавливает 10-байтовые размеры и смещения полей записей Win32 (`24 / 8 / 18` и `12 / 1 / 11`), **но любое чтение или присваивание такого 10-байтового `Extended` проходит транзитом через 53-битный `Double`**, обнуляя младшие 11 бит мантиссы (`prec64=FALSE`, `rt_eq=FALSE`)! Чтобы не повредить чужие 80-битные данные на Win64 при пересылке, их копируют как сырой `TExtended80Rec`, не приводя к `Extended`. Поведение Linux64, macOS64 и ARM остаётся `OPEN` в `EXTENDED_TARGET_PROFILE` (`../SOURCE_ISSUES.md#issue-extended-target-profile`).

## 3. Промежуточная точность и исторические форматы (`{$EXCESSPRECISION}`, `{$REALCOMPATIBILITY}`, `{$SAFEDIVIDE}`)

Даже при одинаковом объявлении `var A, B, C: Single;` результат составного выражения `A * B + C` зависит от ширины промежуточных регистров бэкенда:
- **На x86 (`Win32`):** вещественные выражения классически вычисляются через 80-битный стек сопроцессора x87 (`ST(0)..ST(7)`). По указанию [Floating point precision control (Delphi for x64)](https://docwiki.embarcadero.com/RADStudio/Florence/en/Floating_point_precision_control_(Delphi_for_x64)) директива `{$EXCESSPRECISION}` на 32-битном x86 **не действует**.
- **На x64 (`Win64`):** компилятор использует скалярные инструкции SSE2 на регистрах `XMM`. Локальная директива `{$EXCESSPRECISION ON|OFF}` (карточка EXCESSPRECISION (`../directives/excessprecision.md`), default `ON`) при `ON` расширяет промежуточные операции над `Single` до точности `Double`, а при `OFF` удерживает их в 32-битном `Single` (не сужая переменные типа `Double`).
- **Живые измерения серии P12 (`Delphi 13 CE 37.0.60542.8024`, `0` диагностик):**
  - **`{$REALCOMPATIBILITY ON|OFF}` (`P12_RealCompat_OnOff32`):** подтверждено локальное переключение смысла типа `Real` внутри одного модуля — под `{$REALCOMPATIBILITY ON}` тип `TR48 = Real` занимает **`6` байт** (исторический 48-битный `Real48`), а после `OFF` тип `TR64 = Real` занимает **`8` байт** (`Double`, карточка REALCOMPATIBILITY (`../directives/realcompatibility.md`));
  - **`{$EXCESSPRECISION ON|OFF}` (`P12_ExcessPrecision_Win32/64`):** оба прогона дали `off=1.00000000;on=1.00000000` с `exit=0` (наглядно иллюстрируя правило слоя вычисления: грубое десятичное форматирование скрывает тонкие различия младших `ULP`);
  - **`{$SAFEDIVIDE ON|OFF}` (`P12_SafeDivide32`):** обе ветки вернули `u_on=4.5;u_off=4.5` (`exit=0`) — историческая опция `{$U+}`/`{$U-}` (карточка SAFEDIVIDE (`../directives/safedivide.md`)) относилась только к обходу аппаратного сбоя `FDIV` ранних Pentium (1994) и не защищает от деления на ноль.

## 4. Маски исключений (`SetExceptionMask`), смена default в Athens 12 и `FINITEFLOAT_UNDERSPECIFIED`

Реакция процессора на деление на ноль (`1.0 / 0.0`), неопределённость (`0.0 / 0.0`) и переполнение управляется битами маскирования в аппаратных регистрах **FPU Control Word** (x87) и **MXCSR** (SSE2):
- **Бит замаскирован (включён в множество маски):** аппаратное прерывание **подавляется**, а операция возвращает стандартное значение IEEE 754 (`+Infinity`, `-Infinity`, `NaN`).
- **Бит размаскирован (исключён из маски):** процессор возбуждает аппаратное исключение, которое RTL транслирует в `EZeroDivide`, `EInvalidOp`, `EOverflow`, `EUnderflow`.

### Сигнатура `SetExceptionMask` и исторический перелом в Delphi 12 Athens

Платформенно-независимое управление масками выполняется через [System.Math.SetExceptionMask](https://docwiki.embarcadero.com/Libraries/Florence/en/System.Math.SetExceptionMask):

```pascal
// Документированная кроссплатформенная сигнатура в System.Math (не полный проект)
function SetExceptionMask(const Mask: TArithmeticExceptionMask): TArithmeticExceptionMask;
```

- **Точность типа маски:** каноническая сигнатура `SetExceptionMask` использует тип **`TArithmeticExceptionMask`** (`set of TArithmeticExceptions`, 1 байт). Историческое имя `TFPUExceptionMask` относится к x87-специфичным функциям: в пробе `P2_MathMask_Alias32/64` подтверждено, что они имеют разные `TypeInfo` (`same_typeinfo=FALSE`), поэтому в переносимом коде следует объявлять `TArithmeticExceptionMask`.
- **Перелом умолчания в Delphi 12 Athens:** в классических версиях Delphi (вплоть до 11 Alexandria) критические исключения (`exInvalidOp`, `exZeroDivide`, `exOverflow`) по умолчанию были размаскированы и бросали исключения языка. Начиная с **Delphi 12 Athens**, страница `SetExceptionMask` фиксирует новый default: **все 6 масок FP-исключений включены (`ON`)**. При локальном изменении маски предыдущее значение обязательно возвращают в `try ... finally`.

### Открытый вопрос `FINITEFLOAT_UNDERSPECIFIED` (`../SOURCE_ISSUES.md#issue-finitefloat-underspecified`) (`OPEN`)

1. **Документированное правило:** краткая страница [Finite float](https://docwiki.embarcadero.com/RADStudio/Florence/en/Finite_float) объявляет локальную директиву `{$FINITEFLOAT ON|OFF}` (карточка FINITEFLOAT (`../directives/finitefloat.md`), default `ON`), но **не специфицирует** инструкции и связь с `SetExceptionMask`.
2. **Наблюдения компилятора (`P2` и `P3` на Delphi 13 CE, Win32 и Win64 Debug):** при штатных замаскированных исключениях Athens 12+ деление `1.0 / ZeroVar` вернуло `+Infinity` (`is_inf=TRUE`) **и при `{$FINITEFLOAT ON}`, и при `OFF`**, а после снятия масок `SetExceptionMask([])` в обоих режимах возбуждались `EZeroDivide` (на `1.0 / 0.0`) и `EInvalidOp` (на `0.0 / 0.0`); кроме того, `{$IFOPT FINITEFLOAT ON}` отвергнуто с `E1030`.
3. **Вывод с ограниченной областью:** `{$FINITEFLOAT}` нельзя отождествлять с `SetExceptionMask`; полный межплатформенный контракт остаётся `OPEN`.

## 5. Четыре независимых слоя числовой проверки и полный пример

При верификации численного кода четыре уровня доказательств никогда не подменяют друг друга:
1. **Слой хранения (Storage / ABI):** `SizeOf`, смещения полей и побайтовый `round-trip` через `TExtended80Rec`.
2. **Слой вычисления (Runtime Arithmetic):** подавление компиляторной свёртки констант (чтение операндов из переменных) и побитовая проверка результата до и после округления (`FloatToStr` скрывает младшие биты ULP).
3. **Слой FP-среды (Exception Mask):** фиксация активной `GetExceptionMask` / `SetExceptionMask` непосредственно перед операцией.
4. **Граница receipt:** конкретный замер подтверждает только проверенный таргет и набор опций (матрица доказательств (`62-compiler-evidence.md`)).

## 1. Шесть пластов языка: от физического предела к новому решению

### Пласт I. Статический фундамент `Wirth Pascal -> Turbo / Borland Pascal 1–7`

- **Исходное ограничение эпохи:** однопроходная компиляция на слабых машинах, сегментированная адресация 8086 и жёсткий потолок оперативной памяти DOS (`640 КБ`) без защищённого виртуального адресного пространства. Каждая конструкция обязана была иметь известный на этапе компиляции размер `SizeOf` и обходиться без скрытого менеджера кучи.
- **Физический и грамматический ответ:**
  - **`ShortString` (`string[N]`):** плоский массив `1 + N` байт прямо на стеке или внутри структуры, где байт `S[0]` хранит текущую длину `0..255` (`O(1)` чтение длины, но потолок `255` байт и полное копирование буфера при передаче по значению — глава 09 (`09-strings.md`));
  - **6-байтовый программный `Real48`** для машин без сопроцессора и аппаратные 80-битный `Extended` и 64-битный целочисленный `Comp` для x87 (глава 07 (`07-reals.md`));
  - **битовые шкалы `set of`** фиксированной ширины до `256` элементов (`32` байта — глава 11 (`11-sets.md`)) и плоские записи `record` с вариантным наложением полей `case .. of`;
  - **стековый `object` (`TP 5.5`):** полиморфная структура по значению, где скрытый указатель на VMT лежит внутри самого экземпляра и должен вручную инициализироваться вызовом `constructor`, а также 1-словные процедурные указатели и сегментные средства `near`/`far`, `Mem`/`Port`, `inline($...)`.
- **Почему пласт I упёрся в предел:** передача или присваивание потомка `object` в переменную базового типа по значению вызывала физическую **срезку (*object slicing*)**, отсекая поля наследника; отсутствие единого корня иерархии и метаданных не позволяло построить визуальную среду компонентов Windows и потоковое чтение форм, а лимит `255` символов блокировал работу с реальными текстами.

### Пласт II. Классическая RAD-эпоха, кучевая VMT и COM (`Delphi 1–7`, `1995–2002`)

- **Исходное ограничение эпохи:** переход к событийному GUI Windows, компонентной сборке форм `.dfm` и бинарному взаимодействию системных модулей потребовал ссылочного полиморфизма без срезки, длинных строк и межъязыковых контрактов.
- **Физический и грамматический ответ:**
  - **расщепление старого `object` на value-`record` и кучевой `class(TObject)`:** переменная класса стала 1-словным указателем на кучу; `TObject.InitInstance` гарантированно зануляет память до входа в конструктор; вокруг указателя VMT выстроилась двунаправленная таблица с отрицательными смещениями (RTTI, имя класса, `InstanceSize`, родитель), тип `class of` сделал метакласс первоклассным значением с виртуальными конструкторами, а секция `published` под `{$M+}` дала основу сериализации `.dfm` (главы 24–28 (`24-classes.md`));
  - **2-словный указатель метода `TMethod` (`of object` = `Code + Data`):** связал адрес кода обработчика с конкретным получателем `Self` без владения временем жизни объекта (глава 22 (`22-callables.md`));
  - **кучевой `AnsiString` (Delphi 2):** отрицательный заголовок со счётчиком ссылок `refCount` и длиной + семантика *copy-on-write* (`UniqueString`) сняли барьер `255` байт, сохранив иллюзию типа-значения;
  - **динамический массив `array of T` (Delphi 4):** тот же отрицательный заголовок с `refCount` и длиной в куче, но **без *copy-on-write*** — запись в `B[0]` после `B := A` меняет общий буфер (главный источник ложных аналогий со строками, глава 10 (`10-arrays.md`));
  - **`Variant` / `OleVariant` и COM-интерфейсы `IInterface` (Delphi 3):** автоматический подсчёт ссылок через `_AddRef`/`_Release`, таблицы интерфейсных методов IMT на смещениях внутри объекта и переходники `ADJUSTOR`-thunks, сдвигающие указатель интерфейса обратно к началу `TObject` (глава 29 (`29-interfaces.md`)).
- **Почему пласт II упёрся в предел:** однобайтовый `AnsiString` зависел от системной кодовой страницы Windows и терял символы между локалями; коллекции вроде `TList` строились на нетипизированных `Pointer`; 2-словный `TMethod` не умел захватывать локальные переменные вызывающей процедуры; классическая RTTI видела только `published`-секцию, а ручное `Create`/`Free` классов требовало дисциплины `try..finally`.

### Пласт III. Unicode, мономорфные Generics, замыкания и расширенная RTTI (`Delphi 2005–2010`)

- **Исходное ограничение эпохи:** глобализация ПО, потребность в строго типизированных контейнерах с нативной скоростью, асинхронные коллбэки с захватом контекста и универсальная рефлексия.
- **Физический и грамматический ответ:**
  - **переход `string -> UnicodeString` (UTF-16LE, Delphi 2009):** расширение строкового заголовка полями `codePage` и `elemSize` (`12` байт на `Win32`, `16` байт на `Win64`), литералы в сегменте констант с `refCount = -1`, кодово-страничные `AnsiString(CP)` и транспортный `RawByteString` ([String Types](https://docwiki.embarcadero.com/RADStudio/Florence/en/String_Types_(Delphi)));
  - **мономорфизация `Generics<T>`** (после подготовительного шага `advanced record` с методами и `class operator` в 2006): компилятор порождает для каждой закрытой специализации (`TMonoBox<Integer>`, `TMonoBox<string>`) **отдельный машинный код, собственную VMT и независимые поля `class var`** — прямая противоположность стиранию типов (*type erasure*) в Java ([Declaring Generics](https://docwiki.embarcadero.com/RADStudio/Florence/en/Declaring_Generics), глава 31 (`31-generics.md`));
  - **анонимные методы `reference to`:** поскольку стек процедуры разрушается при возврате, компилятор понижает замыкание в скрытый кучевый объект со счётчиком ссылок COM-интерфейса и выносит захваченные локальные *переменные* (а не их копии!) в разделяемый heap-кадр захвата ([Anonymous Methods](https://docwiki.embarcadero.com/RADStudio/Florence/en/Anonymous_Methods_in_Delphi), глава 23 (`23-closures.md`));
  - **расширенная RTTI (`System.Rtti`, Delphi 2010):** универсальный контейнер `TValue`, пользовательские атрибуты `[CustomAttribute]`, управление эмиссией таблиц через `{$RTTI EXPLICIT}` (глава 36 (`36-rtti.md`)) и прямое восстановление экземпляра `Intf as TObject`.
- **Почему пласт III упёрся в предел:** весь бинарный фундамент по-прежнему проектировался вокруг 32-битного `Win32` (`SizeOf(Pointer) = 4`, 10-байтный x87 `Extended`, стековая цепочка исключений `FS:[0]`), что стало барьером при выходе на 64-битные серверы и мобильные ARM-процессоры.

### Пласт IV. Мультитаргетный ABI и архитектурный урок мобильного ARC (`XE2–10.3`)

- **Исходное ограничение эпохи:** перенос языка на `Win64`, `macOS`, `iOS`, `Android` и `Linux64` с иными соглашениями регистров, шириной адресов и аппаратными правилами раскрутки стека.
- **Физический и грамматический ответ:**
  - введение `Unit Scope Names` (`System.SysUtils`), типов ширины указателя `NativeInt`/`NativeUInt`, переход на `SizeOf(Pointer) = 8`, расширение **`TMethod` (`8 -> 16` байт)** и **`TVarData` (`16 -> 24` байта)**, платформенное расщепление **`Extended`** (`10` байт на `Win32`, `8` байт `Double` на `Win64`/`ARM`, `16` байт на `Linux64` — глава 70 (`70-floating-profiles.md`)) и замена стековых фреймов `FS:[0]` на табличную **`PC-Mapped` раскрутку исключений** ([PC-Mapped Exceptions](https://docwiki.embarcadero.com/RADStudio/Florence/en/PC-Mapped_Exceptions));
  - попытка перенять мобильную модель памяти в **`XE4–10.3` через ARC для `TObject`** на iOS/Android/Linux: каждый объект получал `FRefCount`, разрыв циклов требовал `[Weak]` (обнуляемого через глобальный реестр) или `[Unsafe]`, а принудительная очистка ресурсов шла через `DisposeOf`, переводивший объект в полуразрушенное *zombie state*.
- **Почему пласт IV вызвал обратный поворот:** жизнь в двух несовместимых моделях памяти для одного и того же `class` (`Free` на Windows против ARC и `DisposeOf` на мобильных целях) раскалывала единый исходный код библиотек и нарушала предсказуемость деструкторов.

### Пласт V. Унификация памяти и детерминированный стековый RAII (`10.3 Rio – 10.4 Sydney`)

- **Исходное ограничение эпохи:** требовалось устранить раскол между десктопными и мобильными платформами и одновременно дать языку легковесный детерминированный RAII без аллокаций в куче и громоздких каскадов `try..finally`.
- **Физический и грамматический ответ:**
  - **блочные локальные объявления `var` (`10.3 Rio`):** механизм *inline variable declaration* (в коде пишется `var X := ...` или `for var I := ...` **без** слова `inline`!) сузил область видимости и время жизни управляемых переменных до конкретного блока `begin..end` или одной итерации цикла ([Inline Variable Declaration](https://docwiki.embarcadero.com/RADStudio/Florence/en/Inline_Variable_Declaration));
  - **унификация модели классов (`10.4 Sydney`):** снятие ARC с `TObject` на всех платформах (везде единое классическое владение через `Free` / `Owner`) при сохранении подсчёта ссылок и атрибутов `[weak]`/`[unsafe]` для интерфейсов ([Memory Management](https://docwiki.embarcadero.com/RADStudio/Florence/en/Memory_Management));
  - **Custom Managed Records (`10.4 Sydney`):** операторы `class operator Initialize`, `Finalize`, `Assign` и передача `const [ref]` перенесли автоматический детерминированный RAII прямо на стек и внутрь массивов — с фундаментальной асимметрией отказа: исключение внутри `TObject.Create` автоматически вызывает `Destroy`, тогда как исключение внутри `CMR.Initialize` **не вызывает `Finalize`** ([Custom Managed Records](https://docwiki.embarcadero.com/RADStudio/Florence/en/Custom_Managed_Records), глава 13 (`13-managed-records.md`), глава 68 (`68-lifetime-boundaries.md`)).

### Пласт VI. Аппаратный реализм FP-масок и семантическая точность (`11 Alexandria – 13 Florence`)

- **Исходное ограничение эпохи:** рассогласование немаскированных исключений FPU с внешними C/C++/SIMD-библиотеками, неудобство многострочных шаблонов, избыточность временных переменных в ветвлениях и хрупкость строковых литералов при рефакторинге и локальном переключении директив.
- **Физический и грамматический ответ:**
  - **`11 Alexandria`:** двоичные литералы `%` и разделители цифр `_` для самодокументируемых битовых масок;
  - **`12 Athens`:** включение всех шести масок FP-исключений по умолчанию в RTL (`SetExceptionMask`, возврат IEEE-значений `+Infinity`/`NaN` вместо аварийного `EZeroDivide` — [12 Athens Release 3](https://docwiki.embarcadero.com/RADStudio/Florence/en/12_Athens_-_Release_3), глава 70 (`70-floating-profiles.md`)) и многострочные литералы `'''` с профилем переноса строк TEXTBLOCK (`../directives/textblock.md`);
  - **`13 Florence` (`CompilerVersion = 37.0`):** ленивое условное выражение `if..then..else` (вычисляющее только выбранную ветвь), операторы `is not` и `not in` ([Conditional Operators](https://docwiki.embarcadero.com/RADStudio/Florence/en/Conditional_Operators_(Delphi))), директива `noreturn` в графе потока управления против ложных `W1035` (глава 20 (`20-routines.md`)), разрешаемое на фазе таблицы символов выражение `NameOf(...)` до анализа неиспользуемых присваиваний `H2077` (глава 67 (`67-nameof.md`)), лаконичная форма операторов CMR с **неявным `Self`** (`class operator Initialize;` / `Finalize;`), строгие generic-ограничения `: interface` и `: unmanaged` (отвергающее любые managed-поля и CMR с `E2668` — глава 32 (`32-constraints.md`)), полный стековый откат опций `{$PUSHOPT}`/`{$POPOPT}` и длинные предикаты `{$IFOPT}` ([What's New (Florence)](https://docwiki.embarcadero.com/RADStudio/Florence/en/What%27s_New)).

## 3. Пять инженерных правил на стыках эпох

Там, где в одной строке или структуре встречаются механизмы разных поколений, действуют жёсткие физические границы:

1. **`ShortString` против `UnicodeString` и `{$H-}`:** `ShortString` остаётся однобайтовым буфером `1 + N` на стеке, тогда как неквалифицированный `string` в проверенных профилях `Delphi 13 CE` оставался UTF-16LE `UnicodeString` даже под `{$H-}` (глава 09 (`09-strings.md`)).
2. **Четыре модели структур (`object` vs `record` vs `CMR` vs `class`):** `object` копируется по значению со скрытым VMT-указателем и теряет поля потомка при срезке; обычный `record` тривиален или автоуправляем по полям; `CMR` добавляет пользовательский `Initialize`/`Finalize`/`Assign` без VMT и **без вызова `Finalize` при исключении внутри `Initialize`**; `class` всегда живёт в куче и при исключении в `Create` вызывает `Destroy`.
3. **`TMethod` (`of object`) против `reference to`:** `TMethod` (`8` или `16` байт) не удерживает объект от разрушения, тогда как `reference to` удерживает кучевой COM-кадр по счётчику ссылок и разделяет захваченные локальные *переменные* между всеми копиями замыкания (глава 23 (`23-closures.md`)).
4. **`: record` против `: unmanaged` в обобщениях:** старое ограничение `: record` пропускает записи со строками и CMR, тогда как новое ограничение `Delphi 13` `: unmanaged` требует чистой побитовой тривиальности и отвергает управляемые записи кодом `E2668` (глава 32 (`32-constraints.md`)).
5. **256-элементный фундамент Пласта I внутри оператора `not in` Пласта VI:** новый оператор `X not in [...]` (`Delphi 13`) строится поверх классического конструктора множеств `set of` (`0..255`, `32` байта). На узких перечислениях и малых целых (`0..255`) он разворачивается в быструю битовую проверку, но значения за пределами `0..255` выходят за физический лимит паскалевского множества (глава 11 (`11-sets.md`), глава 17 (`17-expressions.md`)).

# EXTENDEDCOMPATIBILITY — представление совместимости Extended

**Синтаксис:** `{$EXTENDEDCOMPATIBILITY ON}` или `{$EXTENDEDCOMPATIBILITY OFF}`.

**Default в указанном источнике:** `OFF`.

**Scope по документации:** Local (применяется к последующим объявлениям типов и данных с `Extended`).

Директива управляет **бинарным размером хранения** типа [`System.Extended`](https://docwiki.embarcadero.com/Libraries/Florence/en/System.Extended) на платформах, где по умолчанию `Extended` сжат до 8-байтного IEEE-754 `Double` (`Win64` SSE2 и `ARM`, см. [Multi-Device Considerations](https://docwiki.embarcadero.com/RADStudio/Florence/en/Delphi_Considerations_for_Multi-Device_Applications); на `Win32` x87 `Extended` всегда 10 байт, на `Linux64` по System V ABI — 16 байт; глава 07 (`../chapters/07-reals.md`), глава 70 (`../chapters/70-floating-profiles.md`)):
- при **`OFF`** на `Win64` `Extended` занимает `8` байт (`Double`);
- при **`ON`** на `Win64` компилятор выделяет **10 байт** (раскладка [`TExtended80Rec`](https://docwiki.embarcadero.com/Libraries/Florence/en/System.TExtended80Rec)), **но НЕ включает 80-битную арифметику x87**: вычисления идут в 53-битной точности `Double`!

```pascal
{$EXTENDEDCOMPATIBILITY ON}
// Win32: SizeOf(Extended)=10, prec64=TRUE, round-trip TExtended80Rec=TRUE
// Win64: SizeOf(Extended)=10, но prec64=FALSE (SSE2) и round-trip TExtended80Rec=FALSE!
```

**Живые измерения (`Delphi 13 CE 37.0.60542.8024`, проход 0.11 (`../research/COMPILER_PASS_011.md`) и `P13`):**

| Проба / режим | `SizeOf` | `Unpacked` / `Packed` `(Byte, Extended, Byte)` | `prec64` (`1+1e-17<>1`) и round-trip |
|---|---|---|---|
| `OFF` `Win32` (пример 50 (`../../../examples/README.md`), `P13_ExtPrecision_Off32`) | `10` | `24 (E:8,B:18)` / `12 (E:1,B:11)` | `prec64=TRUE`, `rt_eq=TRUE` |
| `OFF` `Win64` (`P13_ExtPrecision_Off64`) | `8` | `24 (E:8,B:16)` / `10 (E:1,B:9)` | `prec64=FALSE`, `rt_eq=TRUE` (`8B`) |
| **`ON` `Win32`** (`P13_ExtCompat_Prec_On32`) | `10` | `24 (E:8,B:18)` / `12 (E:1,B:11)` | `prec64=TRUE`, `rt_eq=TRUE` |
| **`ON` `Win64`** (`P2_ExtCompat_On64`, `P13_ExtCompat_Prec_On64`) | **`10`** | **`24 (E:8,B:18)` / `12 (E:1,B:11)`** | **`prec64=FALSE`, `rt_eq=FALSE`** |

**Ложная аналогия:** в отличие от C `long double` на Linux x86-64, на `Win64` конверсия через `Double` теряет младшие биты мантиссы (`EXTENDED_TARGET_PROFILE` = `OPEN` для не-Windows целей).

Источник: [Embarcadero](https://docwiki.embarcadero.com/RADStudio/Florence/en/Extended_type_compatibility_(Delphi)). Прочитан 18.11.2026.

Статус: сверено с документацией; размеры, смещения полей, `prec64=FALSE` и `rt_eq=FALSE` при `ON` на `Win64` измерены в примере 50 (`../../../examples/README.md`), `P2_ExtCompat_*` и `P13_ExtCompat_Prec_*`.

# INLINE — встраиваемость и место вызова

**Синтаксис:** директива `{$INLINE ON}` / `{$INLINE OFF}` / `{$INLINE AUTO}`; слово `inline;` в заголовке подпрограммы является частью её объявления.

**Default в указанном источнике:** Конфликт слоёв (`INLINE_DEFAULT_PROFILE` (`../SOURCE_ISSUES.md#issue-inline-default-profile`), `OPEN`): *Language Guide* указывает `ON`, а *Compiling* для IDE — `off` (задавайте режим явно).

**Scope по документации:** Двусторонний — учитываются состояние в **точке определения** и состояние в **каждой точке вызова**.

Механизм `inline` (с **Delphi 2005**) работает поверх типизированного IR внутри `.dcu` (глава 72 (`../chapters/72-inline-semantics.md`)):
- **`ON`:** помечает подпрограмму с `inline;` в `.dcu` и разворачивает её тело вместо `call`/`ret` на месте вызова;
- **`OFF`:** подавляет пометку или подстановку на соответствующей стороне;
- **`AUTO`:** рассматривает к встраиванию небольшие непомеченные подпрограммы (до **32 байт** кода по справке).

```pascal
{$INLINE ON}
function MagicAdd(N: Integer): Integer; inline;
begin
  Result := N + $13572468;
end;
```

**Физические измерения машинного кода (`P13_Inline_*`, `Delphi 13 CE` `Win32`):**
Подсчёт константы `$13572468` (`m1`, 3 вызова `MagicAdd; inline;`) и `$24681357` (`m2`, 1 вызов обычной `PlainAdd`) в секциях `.text` / `.itext` PE-образа:
- **`P13_IfOpt_INLINE` / `P13_Inline_IfOpt_Rel`:** `{$IFOPT INLINE ON}` вернул **`ON`** в обоих шаблонах IDE (`Debug` и `Release`);
- **`P13_Inline_Default_Dbg` / `_Rel`:** `.text: m1=0, m2=1`; **`.itext: m1=3, m2=0`** (все 3 вызова физически развёрнуты в `.itext` и в `Debug`, и в `Release`!);
- **`P13_Inline_DefOn_CallOff` и `P13_Inline_DefOff_CallOn`:** **`.text: m1=1, m2=1`; `.itext: 0`** (`{$INLINE OFF}` на *любой* из сторон отменяет подстановку);
- **`P13_Inline_DefAuto_CallOn`:** `.text: m1=0, m2=1`; `.itext: m1=3, m2=0` (`PlainAdd` без `inline;` **между юнитами НЕ авто-встроена**!).

**Ограничения:** правка тела `inline` требует полной пересборки (`Build`) зависимых `.dcu`; не встраиваются `virtual`/`asm`/open arrays/границы `.bpl`; при нехватке модулей в `uses` выдаётся `H2443`. Не путать с C++ ODR, `.dfm` `inline` и TP `inline($8B/...)`.

Источник: [Embarcadero](https://docwiki.embarcadero.com/RADStudio/Florence/en/Calling_Procedures_and_Functions). Прочитан 18.11.2026.

Статус: сверено с документацией; сохранность результата (пример 49 (`../../../examples/README.md`)) и физическая подстановка/отмена в `.itext` измерены в `P13_Inline_*` на `Win32 Debug/Release`.

# PUSHOPT / POPOPT — сохранение и восстановление опций

**Синтаксис:** `{$PUSHOPT} ... {$POPOPT}`.

**Default в указанном источнике:** команды стека опций компилятора; собственного ON/OFF default нет.

**Scope по документации:** `Local` (LIFO-стек внутри текущего модуля).

## Механизм стека опций и открытия серий `P2`–`P3` (`0.11`)

Директивы введены в **Delphi 13 Florence** для локального изменения переключателей (`{$R-}`, `{$Q-}`, `{$J+}`, `{$O-}`, `{$WARNINGS ...}`) с точным возвратом исходного профиля без громоздких проверок `{$IFOPT}` (пример 29 (`../../../examples/README.md`), `0.8`: `on`, `off`, `on`; глава 41 (`../chapters/41-directives.md`), глава 59 (`../chapters/59-directive-profiles.md`)). Вложенные пары работают по принципу LIFO, но **не** сохраняют символы `{$DEFINE}`/`{$UNDEF}`, `.inc`-поток или состояние переменных.

Комментарий «ВЕСЬ стек опций целиком» в сохранённом исходнике ниже неточен: `POPOPT` восстанавливает верхний снимок; нижние снимки остаются в стеке. Сам исходный код сохранён для совпадения с компиляторным свидетельством.

```pascal
// Проверено в P2_PushOpt_Sel_Effect и P3_PushOpt_Discriminate (Delphi 13 CE 37.0)
{$PUSHOPT RANGECHECKS} // хвостовой аргумент не сужает снимок!
  {$R-}{$Q+}
{$POPOPT} // восстанавливает ВЕСЬ стек опций целиком: after_pop R=ON, Q=OFF
```

Живые эксперименты **серий `P2` и `P3`** (COMPILER_PASS_011 (`../research/COMPILER_PASS_011.md`)) выявили две критические границы:
1. **Полный откат вместо выборочного (`PUSHOPT_TABLE_TYPOS`, статус `OPEN`):** несмотря на упоминание именованных аргументов и опечатки `IMPOTEDDATA` / `FINITEFLOATT` в таблице *Option OPT*, в пробах `P2_PushOpt_Sel_Effect` и `P3_PushOpt_Discriminate` вызов `{$POPOPT}` откатил **все изменённые опции целиком (`R=ON; Q=OFF`)**.
2. **Тихое игнорирование опечаток:** пробы `P3_PushOpt_Bogus` (`BOGUS_OPT`), `P3_PushOpt_Typo1` (`FINITEFLOATT`) и `P3_PushOpt_Typo2` (`IMPOTEDDATA`) скомпилировались с **`0` диагностик** (в отличие от `{$IFOPT}`, где опечатки сразу вызвали `E1030`). Семь редких имён таблицы отдельно разобраны в `EXTRA_DIRECTIVES_NOT_REVIEWED` (`../SOURCE_ISSUES.md#issue-extra-directives-not-reviewed`) (EXTRA_OPTIONS.md (`../research/EXTRA_OPTIONS.md`)).

## Защита от ложных аналогий

В отличие от MSVC `#pragma warning(push/pop)`, сохраняющей только предупреждения, `{$PUSHOPT}` фиксирует и кодогенерационные проверки; в отличие от Free Pascal `{$PUSH}`/`{$POP}`, в Delphi 13 используется строго `{$PUSHOPT}`/`{$POPOPT}` — пишите их **без аргументов** (SOURCE_ISSUES (`../SOURCE_ISSUES.md#issue-pushopt-table-typos`)).

Источник: [Embarcadero](https://docwiki.embarcadero.com/RADStudio/Florence/en/Option_OPT_(Delphi)). Прочитан 18.11.2026.

Статус: полный стековый откат и игнор хвостовых имён подтверждены в `0.8` и `P2`–`P3` (`Delphi 13 CE`); `PUSHOPT_TABLE_TYPOS` остаётся `OPEN`.

## Проверка 1.3.0: уточнённые границы

**PUSHOPT_TABLE_TYPOS — PARTIALLY_RESOLVED.** Вложенный include восстанавливает R/Q по стеку. Несогласованный PUSHOPT даёт W1079, POPOPT — W1078 на Win32/64. Прежние хвосты BOGUS_OPT/FINITEFLOATT принимались, но восстанавливался весь набор, поэтому это не доказательство selective subset.

Остаток: Для selective subset нужны официальная точная грамматика/исправление Option OPT или пример Embarcadero с отличимым частичным восстановлением и version-matched compiler. Принятие игнорируемого хвоста ответом не является.

# WARN — конкретный класс предупреждений

**Синтаксис:** `{$WARN identifier ON|OFF|ERROR|DEFAULT}`.

**Default в указанном источнике:** страница говорит об enabled warnings; реальные проектные значения уточняют отдельно.

**Scope по документации:** `Local`, с позиции директивы в тексте.

## Точечная фильтрация против `{$WARNINGS}` и ловушка `DEFAULT`

В отличие от подпрограммного `{$WARNINGS}` (`warnings.md`), `{$WARN}` настраивает **один конкретный класс предупреждений** по его каноническому ID (`SYMBOL_DEPRECATED`, `COMPARING_SIGNED_UNSIGNED`, `HIDDEN_VIRTUAL`, `IMPLICIT_STRING_CAST` и др.; полный каталог из **`76` проверенных в `Delphi 13 CE` ID** приведён в главе 41 (`../chapters/41-directives.md`), профили — в главе 59 (`../chapters/59-directive-profiles.md`)):
- **`ON` / `OFF`** включает или подавляет предупреждение ниже по тексту;
- **`ERROR`** повышает срабатывание этого класса с `Wxxxx` до ошибки компиляции `Exxxx`;
- **`DEFAULT`** возвращает состояние ID из **Project Options (`.dproj` / CLI)**, а не откатывает предыдущий локальный `{$WARN}` в файле; для точного локального отката в Delphi 13 используйте `{$PUSHOPT}` / `{$POPOPT}` (`pushopt-popopt.md`).

## Контрасты `P12` / `P15` и ложная аналогия с MSVC

```pascal
// Проверено в P12_Warn_Granular32 / P12_Warn_Error32 (Delphi 13 CE, Win32 Debug)
{$PUSHOPT}
{$WARN SYMBOL_DEPRECATED OFF}
LegacyProc; // предупреждение W1000 подавлено (diags=[], stdout='legacy')
{$POPOPT}
// При {$WARN SYMBOL_DEPRECATED ERROR} -> отказ: E1000 Symbol 'LegacyProc' is deprecated
```

- **Серия `P12` (`Win32 Debug`):** `OFF` в `P12_Warn_Granular32` подавил `W1000` (`diags=[]`, `run_exit = 0`); `ERROR` в `P12_Warn_Error32` остановил сборку кодом **`E1000`**.
- **Серия `P15` (`Win32 Debug`):** `P15_Warn_Ids_Verified32` приняла без `W1030`/`E1030` **все `76/76`** ID (`run_exit = 0`); `COMPARING_SIGNED_UNSIGNED ERROR` дал **`E1023`** (`P15_Warn_SignedUnsigned_Err32`); скрытие `virtual`-метода без `override`/`reintroduce` относится к **`HIDDEN_VIRTUAL`** (**`W1010`** даже под `HIDING_MEMBER ERROR`, **`E1010`** под `HIDDEN_VIRTUAL ERROR`, `0` диагностик под `OFF`), тогда как не-`virtual` `HIDING_MEMBER` дал `0` диагностик.
- **Ложная аналогия (MSVC):** `#pragma warning(default: 4996)` сбрасывает правило к заводскому умолчанию компилятора, а `{$WARN ... DEFAULT}` подтягивает политику проекта.

Источник: [Embarcadero](https://docwiki.embarcadero.com/RADStudio/Florence/en/Warning_messages_(Delphi)). Прочитан 18.11.2026.

Статус: `W1000`/`E1000` подтверждены в `P12`, а каталог `76/76` ID, `E1023` и контраст `HIDDEN_VIRTUAL` (`W1010`/`E1010`) vs `HIDING_MEMBER` — в серии `P15` (`Delphi 13 CE`, `Win32 Debug`).
