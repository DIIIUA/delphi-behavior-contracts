**Demo Sample Tier:** Level 1 — Basic / Everyday Trap (Dynamic Arrays, Aliasing vs Detachment)


## 1. Three distinct mechanisms behind the keyword `array`

In Object Pascal, the keyword `array` represents three fundamentally different mechanisms with different memory placement, type identity, and calling conventions (ABI). Two of them use the same notation `array of T`, whose meaning is determined entirely by its syntactic position ([Structured Types](https://docwiki.embarcadero.com/RADStudio/Florence/en/Structured_Types_(Delphi)), [Parameters](https://docwiki.embarcadero.com/RADStudio/Florence/en/Parameters_(Delphi))):

| Construct | Where written | Memory and descriptor | Indices and `SizeOf` | Behavior on `:=` and passing |
|---|---|---|---|---|
| **Static array** (`array[Low..High] of T`) | Type, field, or variable declaration | A contiguous inline block of values (stack, data segment, record); no header | Any ordinal range `Low..High`; `SizeOf = Count * SizeOf(T)` | A complete copy of every element (by value) |
| **Dynamic array** (`array of T`) | Type, field, or variable declaration | A pointer to `[0]` on the heap (`nil` at length `0`); a header at negative offsets, `(refCount, length)` | Always `0..Length - 1`; `SizeOf(Var) = SizeOf(Pointer)` (`4`/`8` bytes) | One shared buffer (`refCount`), **without Copy-on-Write on element writes** |
| **Open array** (`array of T`, `array of const`) | **Only** in a formal parameter declaration | At the ABI level, a pair `(PtrToFirst, HighIndex)` without a heap descriptor | Always rebased within the call to **`0..High(Param)`** | Depends on `value` / `const` / `var`; calling `SetLength` is forbidden |

## 2. Syntax, nominal identity, and the formal-parameter trap

```pascal
// Фрагмент грамматики массивов и параметров (не полный проект)
type
  TWeekHours = array[1..7] of Integer;             // статический 1-индексный массив
  TGrid2x3   = array[0..1, 0..2] of Double;        // прямоугольный статический блок
  TNumbers   = array of Integer;                   // именованный динамический массив
  TJagged    = array of array of Integer;          // зубчатый динамический массив

procedure UseDynamic(const A: TNumbers);           // принимает ТОЛЬКО TNumbers (или nil)
procedure UseOpen(const A: array of Integer);      // открытый массив: примет TWeekHours, TNumbers, [1, 2], Slice(...)
procedure UseVarArgs(const Args: array of const);  // вариантный открытый массив (array of TVarRec)
```

*English glosses of the retained source comments:*
- Array and parameter grammar fragment (not a complete project)
- static array indexed from 1
- rectangular static block
- named dynamic array
- jagged dynamic array
- accepts ONLY TNumbers (or nil)
- open array: accepts TWeekHours, TNumbers, [1, 2], Slice(...)
- variant open array (array of TVarRec)



**Two critical typing boundaries:**
1. **`P(A: TNumbers)` is not equivalent to `P(A: array of Integer)`:** the first parameter requires the specific dynamic type `TNumbers` (allows `nil`, and without `const` passes the descriptor with an increment to `refCount` without copying elements); the second is an open array accepting any static or dynamic array of the same element type, a slice `Slice(Arr, Count)`, and a constructor `[10, 20]`, rebasing indices within the procedure body to `0..High(A)`.
2. **Incompatibility of anonymous arrays for `var`/`out`:** two separate declarations `var A: array[0..3] of Integer;` and `var B: array[0..3] of Integer;` create different anonymous types, incompatible with a named `var` parameter (`E2033`). Always declare a shared named type in the `type` section for passing by reference.

## 3. Dynamic-array memory, absence of COW, depth of `Copy`, and open parameters

### Heap descriptor, aliasing, and `SetLength`

Under the [Internal Data Formats](https://docwiki.embarcadero.com/RADStudio/Florence/en/Internal_Data_Formats_(Delphi)) rules, a dynamic-array variable occupies `4` bytes on 32-bit and `8` bytes on 64-bit platforms (`nil` corresponds to an empty array of length `0`). Before element `[0]` on the heap lies a header with reference count `refCount` and length `length` (widened to the platform width on 64-bit targets):
- **No Copy-on-Write for elements:** assignment `B := A` increments `refCount`, after which writing `B[0] := 9` **immediately changes `A[0]`**, because both variables refer to one buffer!
- **Making a buffer unique through `SetLength` ([System.SetLength](https://docwiki.embarcadero.com/Libraries/Florence/en/System.SetLength)):** a call to `SetLength(B, NewLen)` — including `SetLength(B, Length(B))` with the previous length — guarantees `refCount = 1`: if the buffer was shared (`refCount > 1`), a new block is allocated and the elements are copied, isolating `B` from `A` (confirmed by example 01 (`../../../examples/01-array-alias.dpr`), `OBSERVED_PASS` on Delphi 13 Win32 Debug: output `9`, `9`, `12`). New cells are zeroed on extension (`Default(T)`), and discarded cells are finalized on truncation.

### The shallowness of `Copy` and multidimensional arrays

- **`Copy(A)` / `Copy(A, Index, Count)`:** creates a new outer dynamic array, but performs a **shallow copy** of the elements. If the elements are references to `class` instances, interfaces, or nested dynamic arrays (`TJagged`), the inner rows and objects remain shared between `A` and the copy!
- **Rectangular versus jagged arrays:** static `array[0..1, 0..2] of Double` is one contiguous memory block (row-major); dynamic `array of array of Integer` is an array of pointers to independent one-dimensional heap arrays, where each row may have its own length or be `nil`.

### Dynamic-array operations (XE7+): `Insert`, `Delete`, `Concat`, operator `+`, `Copy`, and aliasing vs detachment

Starting with the **Delphi XE7+** line, dynamic arrays gained built-in concatenation and structural-modification operations without manual `Move` and `SetLength` loops. The dual-architecture probes **`P15_DynArray_Ops32`** (`Win32`, `pe=0x14c`, `0` diagnostics, `run_exit = 0`) and **`P15_DynArray_Ops64`** (`Win64`, `pe=0x8664`, `0` diagnostics, `run_exit = 0`) verified every operation and the exact boundary between buffer sharing (*aliasing*) and detaching a copy (*detachment*):

```pascal
// Иллюстративный фрагмент (проверено в P15_DynArray_Ops32 / P15_DynArray_Ops64)
A := [1, 2, 3];
B := [4, 5];
C := A + B;                  // C_plus=[1,2,3,4,5]
D := Concat(A, B, [6]);      // D_concat=[1,2,3,4,5,6]
Insert(99, C, 1);            // C_ins1=[1,99,2,3,4,5] — вставка одного элемента по 0-индексу
Insert([77, 88], C, 0);      // C_ins_sub=[77,88,1,99,2,3,4,5] — вставка подмассива
Delete(C, 2, 2);             // C_del=[77,88,2,3,4,5] — удаление 2 элементов с индекса 2
E := Copy(C, 1, 3);          // E_copy=[88,2,3] — срез 3 элементов с индекса 1
```

*English glosses of the retained source comments:*
- Illustrative fragment (tested in P15_DynArray_Ops32 / P15_DynArray_Ops64)
- C_ins1=[1,99,2,3,4,5] — inserting one element using 0-based indexing
- C_ins_sub=[77,88,1,99,2,3,4,5] — inserting a subarray
- C_del=[77,88,2,3,4,5] — deleting 2 elements starting at index 2
- E_copy=[88,2,3] — a slice of 3 elements starting at index 1



| Operation on an alias (`Alias* := A`, where `A = [10, 2, 3]`, `refCount > 1`) | Does it change the original `A`? | Measured `stdout` in `P15_DynArray_Ops32` / `64` |
|---|---|---|
| Element write `Alias[0] := 10` (on original `[1, 2, 3]`) | **Yes** (writes to the shared buffer) | `A_after_alias=[10,2,3]` |
| Insertion `Insert(55, Alias2, 0)` | **No** (detaches a new copy) | `A_after_insert=[10,2,3];Alias2=[55,10,2,3]` |
| Deletion `Delete(Alias3, 0, 1)` | **No** (detaches a new copy) | `A_after_delete=[10,2,3];Alias3=[2,3]` |
| Length change `SetLength(Alias4, 5)` | **No** (detaches a new copy) | `A_after_setlength=[10,2,3];Alias4_len=5` |

The fundamental conclusion from these probes: indexed writing `Alias[I] := X` changes the shared buffer in place. In the tested structure/size-changing calls (`Insert`, `Delete`, `SetLength`) under `refCount > 1`, the target variable's buffer becomes unique (*detachment*); other variables continue to reference the former buffer. These observations do not establish behavior for all arguments, including no-op operations.

### Cost and limitations of open arrays (`value` / `const` / `var`)

- **An open array by value (`procedure P(A: array of Integer)`):** on procedure entry, the compiler allocates a local buffer and **copies every element** of the supplied sequence (freeing the copy on exit); for large arrays, this creates hidden overhead (while objects within the elements are still not cloned).
- **By `const` (`const A: array of Integer`):** no element copy is made — only the pair `(Ptr, High)` is passed, and writing to `A[i]` is forbidden by the compiler (but the array's contents are not protected against modification through an external alias).
- **By `var` (`var A: array of Integer`):** directly mutates the caller's original array; passing temporary constructor `[1, 2]` to a `var` parameter is forbidden and rejected with error `E2197` (confirmed by negative pair 06 (`../../../examples/README.md`) on Delphi 13 Win32 Debug).

## 1. Two levels of record management: from automatic fields to CMR

In the Delphi memory model ([Memory Management](https://docwiki.embarcadero.com/RADStudio/Florence/en/Memory_Management), [Custom Managed Records](https://docwiki.embarcadero.com/RADStudio/Florence/en/Custom_Managed_Records)), the compiler manages the lifetime of a record (`record`) at two levels:

1. **An automatically managed record (a record with built-in managed fields):** as soon as an ordinary `record` includes at least one field of type `string`, a dynamic array, `IInterface`, `Variant`, or a nested managed record, the compiler creates an RTTI table of managed-field offsets for it and automatically inserts calls to RTL procedures (`_InitializeRecord`, `_FinalizeRecord`, `_CopyRecord`), wrapping the variable’s lifetime in a hidden `try ... finally` block.
2. **Custom Managed Records (CMR, introduced in Delphi 10.4 Sydney):** allow the developer to declare custom lifecycle hooks — `class operator Initialize`, `Finalize`, and `Assign`. This turns the record into a deterministic lifetime container (for OS handles, unmanaged buffers, locks, state logs), integrated directly into code generation for prologues, epilogues, arrays, and exception unwinding.

## 2. Operator syntax: the classic 10.4+ form and implicit `Self` in Delphi 13

  TManagedResource = record
  strict private

The compiler’s signature requirements are strict:
- **`Initialize(out Dest: TRec)`:** must take exactly one `out` parameter of the record’s own type. The `out` modifier emphasizes that on entry, the scalar fields of `Dest` contain **uninitialized stack/heap bytes** (the compiler zero-initializes nested automatically managed fields before entering user code).
- **`Finalize(var Dest: TRec)`:** takes one `var` parameter of the record type; called when leaving scope, unwinding an exception, destroying the containing object/array, or during unit `finalization`.
- **`Assign(var Dest: TRec; const [ref] Src: TRec)`:** intercepts `Dest := Src` copying (unlike the `Implicit`/`Explicit` type-cast operators discussed in chapter 33 (`33-operators.md`)). The second parameter must have the **`const [ref]`** qualifier; otherwise, passing `Src` by value would cause infinite recursive `Assign` calls!

## 3. Hidden call sites, `Assign` invariants, and parameter passing

### Where the compiler calls CMR operators and why copies must not be counted

- **Local `var` versus `inline var`:** an ordinary local variable is initialized in the subroutine prologue and finalized on exit (example 19 (`../../../examples/19-managed-record.dpr`), `OBSERVED_PASS`: `5`, `1`); a block-scoped `inline var R: TRec` is initialized at its declaration point within a nested `begin ... end` and finalized on leaving that block (chapter 16 (`16-variables.md`)).
- **Arrays, objects, and the heap:** when a class is created or an array is extended with `SetLength`, `Initialize` is called for each element; on destruction/shrinking, `Finalize` is called (if an exception occurs while initializing the `K`th array element, only the successfully created `0..K-1` elements will be finalized). For manual heap storage, `New(P)` and `Dispose(P)` automatically call `Initialize`/`Finalize`, whereas raw `GetMem`/`FreeMem` **ignore** them and require explicit [System.Initialize](https://docwiki.embarcadero.com/Libraries/Florence/en/System.Initialize) / `System.Finalize` (chapter 14 (`14-pointers.md`)).
- **Do not rely on the exact number of copies:** returning a function through `Result`, passing temporary expressions, and optimizations (copy elision) may change the number of `Initialize`/`Assign`/`Finalize` calls between versions and platforms. Ownership logic must rely on correct reference counting or ownership transfer, rather than an expected fixed call count.

### Two mandatory protections inside `Assign`

On entry into `Assign(var Dest; const [ref] Src)`, the `Dest` variable **is already initialized** and may own an active resource. Therefore, any resource-handling implementation of `Assign` must:
1. **Guard against self-assignment (`A := A`):** first check `if @Dest = @Src then Exit;` (otherwise, releasing the old `Dest` resource will destroy the `Src` source!). Example 39 (`../../../examples/README.md`) (`OBSERVED_PASS`: `9`, `9`) shows this address check on a scalar field, but a real handle or buffer requires the second step as well;
2. **Release the previous `Dest` resource** (or decrement its reference count) before writing the new resource from `Src`; otherwise, the previous handle will leak.

### Parameter-passing matrix (confirmed by example 47 (`../../../examples/README.md`))

| Parameter declaration | Lifetime and copying behavior |
|---|---|
| `ByValue(R: TRec)` | A separate local copy is created (`Initialize` + `Assign` or copying), finalized on leaving `ByValue`; the caller’s original does not change |
| `ByVar(var R: TRec)` | A direct reference to the existing instance is passed without `Initialize`/`Assign`/`Finalize` |
| `ByConstRef(const [ref] R: TRec)` | Guarantees read-only passing by reference without creating a temporary copy or calling `Assign` |
| `ByConst(const R: TRec)` | Passed without a copy in the CMR documentation examples, but in the general ABI, `const` without `[ref]` depends on size/platform; for predictably avoiding copying with CMR, `const [ref]` is preferable |

Under the official [Custom Managed Records](https://docwiki.embarcadero.com/RADStudio/Florence/en/Custom_Managed_Records) contract, confirmed by a live run of example 37 (`../../../examples/README.md`) (`OBSERVED_PASS` on Delphi 13 Win32 Debug: output `caught` and `FinalizeCount = 0`):

**Demo Sample Tier:** Level 3 — Advanced (Generics, Generic Methods, HasWeakRef / GetTypeKind / E2533)


Generics (introduced in **Delphi 2009**, [Declaring Generics](https://docwiki.embarcadero.com/RADStudio/Florence/en/Declaring_Generics)) allow classes, records, interfaces, dynamic arrays, procedural types, and methods to be parameterized with formal type parameters. Within its own declaration, `TBox<T>` acts as an **open form**, and substituting a concrete type (`TBox<Integer>`, `TBox<string>`) produces a **closed specialization** (constructed type) with its own physical layout and class data.

## Specialization mechanics versus type erasure and C++ templates

Delphi generics differ fundamentally both from Java's type-erasure model and from textual, duck-typed template instantiation in C++:

1. **Checking the body at the declaration point (versus C++ `template`).** The compiler checks the open `TBox<T>` body once against its declared constraints (chapter 32 (`32-constraints.md`)). Without constraints, `T` is treated as an opaque value: it can be stored, copied through `:=`, passed, and returned, but `T.Create` cannot be called, `A + B` cannot be added, `A = B` cannot be compared, and unconfirmed members cannot be accessed.
2. **Actual distinct types in binary code (versus Java).** Each closed specialization receives its own runtime representation:
   - **Memory layout:** field `Value: T` occupies exactly `SizeOf(T)` bytes with `T` alignment, so `TBox<Byte>` and `TBox<Int64>` have different `InstanceSize` values.
   - **Managed-field table:** if argument `T` is managed (`string`, `IInterface`, a dynamic array, CMR), this specialization receives its own `vmtInitTable`, which automatically zeros and finalizes field `Value` (chapter 35 (`35-memory.md`)).
   - **Separate `class var`:** each closed specialization is allocated **its own independent static-data cell** ([Class Variable in Generics](https://docwiki.embarcadero.com/RADStudio/Florence/en/Class_Variable_in_Generics)). Because code is generated for each specialization, a large number of closed instantiations increases the size of the `.dcu` and executable file.

### Compile-time intrinsics for specialization optimization: `GetTypeKind(T)`, `IsManagedType(T)`, `HasWeakRef(T)`

Within a generic type or method body, compile-time expressions `SizeOf(T)`, `Default(T)`, `TypeInfo(T)` are available, and starting with **Delphi XE7**, so are compiler intrinsics `GetTypeKind(T)`, `IsManagedType(T)`, and `HasWeakRef(T)`. Since their results are constant in each closed specialization, branches such as `if IsManagedType(T) then ...` are folded at compile time without runtime branching overhead. Expression `Default(T)` returns the type's zero value (`0`, `False`, `nil`, `''`, a zeroed record), and assignment `Value := Default(T)` for managed `T` releases the previous string buffer or interface through the normal mechanism.

## Formal grammar and declaration restrictions

```pascal

```

*English glosses of the retained source comments:*
- Syntax excerpt showing permitted generic constructs (not a complete project)
- Generic dynamic array (NOT an open array!)
- Generic procedural type
- Generic method inside a class/record



Five strict syntactic rules:
1. **No free (top-level) generic routines.** Unlike C++ and C# local functions, Delphi does not allow a free `function Max<T>(const A, B: T): T;` at unit level — generic routines are declared **only as class or record methods** (example 10 (`../../../examples/README.md`), `OBSERVED_PASS`: `TIdentity.Keep<Integer>(42)` outputs `42`). The type-parameter list is repeated in the implementation header (`class function TIdentity.Keep<T>(const Value: T): T;`), but without repeating constraints `: record` / `: class`.
2. **No polymorphic generic methods (`E2533`).** Constructors, destructors, and `virtual`, `dynamic`, `message` methods cannot declare their own type-parameter list `<U>` (the fixed table of class VMT slots cannot accommodate a set of future method specializations that is unknown in advance).
3. **Type-parameter scope and ancestry.** Parameter `T` from `TBox<T>` is not automatically inherited as a name in the descendant header: write `TChild<S> = class(TBox<S>)`. A class ancestor may be an ordinary class or a specialized generic class (`class(TBox<Integer>)`, `class(TBox<S>)`), but **not** a bare type parameter (`class(T)` is forbidden).
4. **Specialization aliases.** Declaration `type TIntCounter = TCounter<Integer>;` denotes the very same specialization, rather than a new distinct type.
5. **No partial specialization or nontype parameters.** Unlike C++ (`template<typename T, int N>`), parameters in `<...>` always denote only types, and explicitly overloading the template body for one concrete type is not supported.

## 1. Classification, comma syntax, and overloaded short letters

Compiler directives in Embarcadero Delphi are written inside `{$...}` or `(*$...*)` comments, where the `$` character must follow the opening delimiter **immediately**, without a space (the `{ $R+}` form is an ordinary comment that the compiler silently skips). By nature, all directives fall into three families ([Compiler Directives List](https://docwiki.embarcadero.com/RADStudio/Florence/en/Delphi_Compiler_Directives_(List)_Index), [Delphi compiler directives](https://docwiki.embarcadero.com/RADStudio/Florence/en/Delphi_compiler_directives)):

1. **Switches (`Switch directives`):** have the single-letter `{$R+}` / `{$R-}` forms and the long `{$RANGECHECKS ON}` / `{$RANGECHECKS OFF}` forms.
   - **The comma rule (example 45 (`../../../examples/README.md`), `OBSERVED_PASS`):** single-letter switches may be grouped with commas and no spaces (`{$B+,R-}`), whereas in a long form, text after the first switch and a space/comma is treated as a trailing comment and **does not enable** a second directive! Long directives are therefore always written in separate `{$BOOLEVAL ON}{$RANGECHECKS OFF}` blocks.
2. **Parameterized directives (`Parameter directives`):** pass a filename, number, identifier, or filter to the compiler or linker (`{$ALIGN 8}`, `{$MINENUMSIZE 4}`, `{$APPTYPE CONSOLE}`, `{$WARN SYMBOL_DEPRECATED ERROR}`, `{$RTTI EXPLICIT ...}`).
3. **Conditional directives (`Conditional directives`):** control source-text selection before syntax analysis (`{$DEFINE}`, `{$UNDEF}`, `{$IFDEF}`, `{$IFNDEF}`, `{$IF}`, `{$ELSEIF}`, `{$ELSE}`, `{$ENDIF}`, `{$IFEND}`, `{$IFOPT}`; see chapter 42 (`42-conditionals.md`)).

### Collisions between single-letter forms

Historically, the same letter in a short form serves entirely different mechanisms depending on its argument:

| Letter | Switch (`+` / `-`) | Parameterized / other form |
|---|---|---|
| `$R` | `{$R+}` / `{$R-}` — range-bound checking (`RANGECHECKS`) | `{$R file.res [Pred]}` — linking a resource file (`RESOURCE`) |
| `$I` | `{$I+}` / `{$I-}` — generating file input/output checks (`IOCHECKS`) | `{$I file.inc}` — lexical source-text insertion (`INCLUDE`) |
| `$M` | `{$M+}` / `{$M-}` — classic RTTI for the `published` section (`TYPEINFO`) | `{$M minstack,maxstack}` — executable-image stack sizes (`MINSTACKSIZE`/`MAXSTACKSIZE`) |
| `$A` | `{$A+}` / `{$A-}` — default field alignment / no alignment | `{$A1}`, `{$A2}`, `{$A4}`, `{$A8}`, `{$A16}` — an explicit `ALIGN` step |
| `$D` | `{$D+}` / `{$D-}` — debugger line numbers (`DEBUGINFO`) | `{$D 'text'}` — a module description string (`DESCRIPTION`); `{$D0..D2}` — see chapter 71 (`71-compilation-layers.md`) |
| `$L` | `{$L+}` / `{$L-}` — local symbol table (`LOCALSYMBOLS`) | `{$L file.obj}` — including an external object module (`LINK`) |

## 2. Four scopes and changes in modern versions (`PUSHOPT` / `IFOPT`)

Besides the distinction between `Global` (for the whole unit, before `interface`/`uses`) and `Local` (from the point encountered downward through the text), it is critical to distinguish:
- **Whole-subroutine granularity:** options such as `{$OPTIMIZATION}` (`{$O}`) and `{$STACKFRAMES}` (`{$W}`) apply to the entire procedure, rather than one line inside `begin..end`.
- **Being fixed in the type declaration:** `{$ALIGN}`, `{$MINENUMSIZE}`, `{$SCOPEDENUMS}`, and the scaled address-arithmetic property of a typed pointer (pointer-arithmetic card (`../directives/pointermath.md`), example 26 (`../../../examples/README.md`)) are retained by the type itself at the `type T = ...;` point.
- **Lexical literal directives (Delphi 12+):** control of multiline-literal line-break format `'''` (`CRLF` versus `LF`, multiline-literal card (`../directives/textblock.md`), example 28 (`../../../examples/README.md`), and live probe `P7_TextBlock_CRLF_LF` with length `12` versus `11` and automatic removal of the closing `'''` indentation).

In **Delphi 13 Florence**, the option stack and state checking received key updates ([What's New](https://docwiki.embarcadero.com/RADStudio/Florence/en/What%27s_New), [Option OPT](https://docwiki.embarcadero.com/RADStudio/Florence/en/Option_OPT_(Delphi)), [IFOPT](https://docwiki.embarcadero.com/RADStudio/Florence/en/IFOPT_directive_(Delphi))):
- **`{$PUSHOPT}` and `{$POPOPT}`** (PUSHOPT card (`../directives/pushopt-popopt.md`), example 29 (`../../../examples/README.md`), `OBSERVED_PASS`: `on`, `off`, `on`) save and restore supported compiler-option states without manual branching;
- **`{$IFOPT}` with long names** (example 44 (`../../../examples/README.md`), `OBSERVED_PASS`: `scoped`, `flat`) allows switches without a short single-letter code to be tested, for example `{$IFOPT SCOPEDENUMS ON}`.

## 1. Why the name `Extended` alone is insufficient

In Object Pascal source text, type `System.Extended` is written the same way on every platform, but at the binary-representation and machine-register levels it splits into different profiles. According to the [System.Extended](https://docwiki.embarcadero.com/Libraries/Florence/en/System.Extended) and [Multi-Device Considerations](https://docwiki.embarcadero.com/RADStudio/Florence/en/Delphi_Considerations_for_Multi-Device_Applications) tables:

| Target platform (CPU / OS) | `SizeOf(Extended)` | Hardware organization and significant boundary |
|---|---|---|
| Intel Win32 (x86) | **10 bytes** | Hardware 80-bit x87 FPU format (1 sign bit + 15 exponent bits + an **explicit** integer bit + 63 fraction bits) |
| Intel Win64 (x64, under `{$EXTENDEDCOMPATIBILITY OFF}`) | **8 bytes** | An alias of IEEE `Double` (`binary64`, 53 significant mantissa bits in SSE2 `XMM` registers) |
| Intel Linux64 / Intel macOS64 | **16 bytes** | An 80-bit x87 value with 6 padding bytes under the System V ABI (**not** IEEE `binary128`!) |
| ARM (Android, iOS, macOS ARM64) | **8 bytes** | An alias of IEEE `Double` (including Apple Silicon ARM64; do not confuse it with an old macOS Intel example lacking a CPU specification) |

## 2. Storage compatibility (`{$EXTENDEDCOMPATIBILITY}`, `TExtended80Rec`) and `EXTENDED_TARGET_PROFILE` (`../SOURCE_ISSUES.md#issue-extended-target-profile`)

When porting binary files and records between Win32 and 64-bit targets, strictly distinguish **storage-buffer size** from **the precision of the arithmetic itself**:

- **`{$EXTENDEDCOMPATIBILITY ON|OFF}` (EXTENDEDCOMPATIBILITY card (`../directives/extendedcompatibility.md`), default `OFF`):** the local directive on [Extended type compatibility](https://docwiki.embarcadero.com/RADStudio/Florence/en/Extended_type_compatibility_(Delphi)) switches `Extended` to a 10-byte storage format for binary compatibility of structures. On Win64, however, it **does not enable 80-bit x87 arithmetic**: calculations use a 53-bit `Double` mantissa on SSE2!
- **`System.TExtended80Rec` ([TExtended80Rec](https://docwiki.embarcadero.com/Libraries/Florence/en/System.TExtended80Rec)):** a packed 10-byte record (`Words`, `Bytes`, `Frac`, `Exp`, `Sign`), explicitly separating serialization of 80-bit data streams from the current platform's arithmetic type.

### Decisive measurements in series P13 (`P13_ExtCompat_Prec_On32/64` and `P13_ExtPrecision_Off32/64`, `OPEN` for non-Windows)

Series **P13** on `Delphi 13 CE` (`37.0.60542.8024`, `Win32` `0x14c` and `Win64` `0x8664`, Debug, `0` diagnostics; alongside example 50 (`../../../examples/README.md`)) simultaneously measured `SizeOf`, field offsets in `TUnpacked = record A: Byte; E: Extended; B: Byte; end` and `TPacked = packed record A: Byte; E: Extended; B: Byte; end`, the 64-bit-mantissa test `prec64 = ((1.0 + 1e-17) <> 1.0)`, and the bytewise `round-trip` `Extended -> TExtended80Rec -> Extended`:

| Mode and target | `SizeOf(Extended)` / `TExtended80Rec` | `TUnpacked` (`SizeOf; offE; offB`) | `TPacked` (`SizeOf; offE; offB`) | `prec64` (`1 + 1e-17 <> 1`) | Bytewise `round-trip` (`rt_eq`) |
|---|---|---|---|---|---|
| **Win32** `OFF` and **`ON`** (`P13_ExtCompat_Prec_On32`) | `10` / `10` | `24; offE=8; offB=18` | `12; offE=1; offB=11` | **`TRUE`** (x87 64-bit mantissa) | **`TRUE`** (`0AC264DA3FE0E9F60540`) |
| **Win64** `OFF` (`P13_ExtPrecision_Off64`) | `8` / `10` | `24; offE=8; offB=16` | `10; offE=1; offB=9` | **`FALSE`** (SSE2 `Double`) | `TRUE` (`984CFB073CDD5E40` is already an 8-byte `Double`) |
| **Win64** **`{$EXTENDEDCOMPATIBILITY ON}`** (`P13_ExtCompat_Prec_On64`) | **`10` / `10`** | **`24; offE=8; offB=18`** | **`12; offE=1; offB=11`** | **`FALSE`** (the arithmetic is still `Double`!) | **`FALSE`!** (10 bytes `0AC264DA3FE0E9F60540` are truncated through `Double`!) |

**Key physical conclusion:** on `Win64`, directive `{$EXTENDEDCOMPATIBILITY ON}` exactly restores Win32's 10-byte record-field sizes and offsets (`24 / 8 / 18` and `12 / 1 / 11`), **but any reading or assignment of such a 10-byte `Extended` passes through a 53-bit `Double`**, zeroing the low 11 mantissa bits (`prec64=FALSE`, `rt_eq=FALSE`)! To avoid damaging someone else's 80-bit data when forwarding it on Win64, copy it as raw `TExtended80Rec` without casting to `Extended`. Linux64, macOS64, and ARM behavior remains `OPEN` in `EXTENDED_TARGET_PROFILE` (`../SOURCE_ISSUES.md#issue-extended-target-profile`).

## 3. Intermediate precision and historical formats (`{$EXCESSPRECISION}`, `{$REALCOMPATIBILITY}`, `{$SAFEDIVIDE}`)

Even with the same `var A, B, C: Single;` declaration, the result of compound expression `A * B + C` depends on the width of the backend's intermediate registers:
- **On x86 (`Win32`):** real expressions are traditionally computed through the x87 coprocessor's 80-bit stack (`ST(0)..ST(7)`). According to [Floating point precision control (Delphi for x64)](https://docwiki.embarcadero.com/RADStudio/Florence/en/Floating_point_precision_control_(Delphi_for_x64)), directive `{$EXCESSPRECISION}` **has no effect** on 32-bit x86.
- **On x64 (`Win64`):** the compiler uses scalar SSE2 instructions on `XMM` registers. Local directive `{$EXCESSPRECISION ON|OFF}` (EXCESSPRECISION card (`../directives/excessprecision.md`), default `ON`), when `ON`, widens intermediate operations on `Single` to `Double` precision; when `OFF`, it keeps them in 32-bit `Single` (without narrowing `Double` variables).
- **Live measurements in series P12 (`Delphi 13 CE 37.0.60542.8024`, `0` diagnostics):**
  - **`{$REALCOMPATIBILITY ON|OFF}` (`P12_RealCompat_OnOff32`):** local switching of the meaning of type `Real` within a single unit was confirmed — under `{$REALCOMPATIBILITY ON}`, type `TR48 = Real` occupies **`6` bytes** (historical 48-bit `Real48`), while after `OFF`, type `TR64 = Real` occupies **`8` bytes** (`Double`, REALCOMPATIBILITY card (`../directives/realcompatibility.md`));
  - **`{$EXCESSPRECISION ON|OFF}` (`P12_ExcessPrecision_Win32/64`):** both runs produced `off=1.00000000;on=1.00000000` with `exit=0` (clearly illustrating the computation-layer rule: coarse decimal formatting conceals subtle differences in the low `ULP`);
  - **`{$SAFEDIVIDE ON|OFF}` (`P12_SafeDivide32`):** both branches returned `u_on=4.5;u_off=4.5` (`exit=0`) — the historical `{$U+}`/`{$U-}` option (SAFEDIVIDE card (`../directives/safedivide.md`)) only concerned working around the hardware `FDIV` defect in early Pentium processors (1994) and does not protect against division by zero.

## 4. Exception masks (`SetExceptionMask`), the default change in Athens 12, and `FINITEFLOAT_UNDERSPECIFIED`

The processor's response to division by zero (`1.0 / 0.0`), an indeterminate result (`0.0 / 0.0`), and overflow is controlled by masking bits in the hardware **FPU Control Word** (x87) and **MXCSR** (SSE2) registers:
- **Bit masked (included in the mask set):** the hardware interrupt is **suppressed**, and the operation returns a standard IEEE 754 value (`+Infinity`, `-Infinity`, `NaN`).
- **Bit unmasked (excluded from the mask):** the CPU raises a hardware exception, which the RTL maps to `EZeroDivide`, `EInvalidOp`, `EOverflow`, `EUnderflow`.

### The `SetExceptionMask` signature and the historical change in Delphi 12 Athens

Platform-independent mask control is performed through [System.Math.SetExceptionMask](https://docwiki.embarcadero.com/Libraries/Florence/en/System.Math.SetExceptionMask):

```pascal
// Документированная кроссплатформенная сигнатура в System.Math (не полный проект)
function SetExceptionMask(const Mask: TArithmeticExceptionMask): TArithmeticExceptionMask;
```

*English glosses of the retained source comments:*
- Documented cross-platform signature in System.Math (not a complete project)



- **The exact mask type:** the canonical `SetExceptionMask` signature uses type **`TArithmeticExceptionMask`** (`set of TArithmeticExceptions`, 1 byte). Historical name `TFPUExceptionMask` belongs to x87-specific functions: probe `P2_MathMask_Alias32/64` confirmed that their `TypeInfo` values differ (`same_typeinfo=FALSE`), so portable code should declare `TArithmeticExceptionMask`.
- **The default change in Delphi 12 Athens:** in classic Delphi versions (through 11 Alexandria), critical exceptions (`exInvalidOp`, `exZeroDivide`, `exOverflow`) were unmasked by default and threw language exceptions. Starting with **Delphi 12 Athens**, page `SetExceptionMask` records a new default: **all 6 FP-exception masks are enabled (`ON`)**. When changing the mask locally, always restore its previous value in `try ... finally`.

### Open question `FINITEFLOAT_UNDERSPECIFIED` (`../SOURCE_ISSUES.md#issue-finitefloat-underspecified`) (`OPEN`)

1. **Documented rule:** the short [Finite float](https://docwiki.embarcadero.com/RADStudio/Florence/en/Finite_float) page declares local directive `{$FINITEFLOAT ON|OFF}` (FINITEFLOAT card (`../directives/finitefloat.md`), default `ON`), but **does not specify** the instructions or relationship with `SetExceptionMask`.
2. **Compiler observations (`P2` and `P3` on Delphi 13 CE, Win32 and Win64 Debug):** with ordinary Athens 12+ masked exceptions, division `1.0 / ZeroVar` returned `+Infinity` (`is_inf=TRUE`) **under both `{$FINITEFLOAT ON}` and `OFF`**; after unmasking through `SetExceptionMask([])`, both modes raised `EZeroDivide` (on `1.0 / 0.0`) and `EInvalidOp` (on `0.0 / 0.0`); additionally, `{$IFOPT FINITEFLOAT ON}` was rejected with `E1030`.
3. **Scoped conclusion:** `{$FINITEFLOAT}` cannot be equated with `SetExceptionMask`; the complete cross-platform contract remains `OPEN`.

# 73. From old to new: the underlying logic of Delphi language evolution

> **[DEMO EDITION — Evaluation Sample]** This package is the free evaluation demo of **Delphi Behavior Contracts v1.0.0** (full edition: 74 complete EN/RU chapters, 89 full directive cards, 879+ compiler observations). **Demo Sample Tier:** Level 4 — Architectural Synthesis (Six Historical Strata: Turbo Pascal to Delphi 13)


At first acquaintance, modern `Delphi 13 Florence` may seem a paradoxical fusion of distant eras: the same `.pas` unit compiles, side by side, `ShortString` and the stack-based `object` from the MS-DOS era, heap-allocated `TObject` classes with VMT tables and `IInterface` COM interfaces, monomorphized `Generics<T>` generics, `reference to` closures, deterministic managed records with implicit `Self`, and lazy `if..then..else` conditional expressions. Behind this diversity lies a strict **cause-and-effect logic**, rather than an accidental accumulation of syntax: the physical and architectural constraints of each stratum inevitably gave rise to the next mechanism, while industrial continuity requirements kept all preceding strata within a single compiler (`dcc32`/`dcc64` `37.0`).

---

## 1. Six language strata: from a physical limit to a new solution

### Stratum I. The static foundation `Wirth Pascal -> Turbo / Borland Pascal 1–7`

- **The era's initial constraint:** single-pass compilation on weak machines, segmented 8086 addressing, and the hard DOS RAM ceiling (`640 KB`) without a protected virtual address space. Every construct had to have a compile-time-known `SizeOf` size and operate without a hidden heap manager.
- **The physical and grammatical response:**
  - **`ShortString` (`string[N]`):** a flat array of `1 + N` bytes directly on the stack or inside a structure, where byte `S[0]` stores the current length `0..255` (`O(1)` length reading, but a ceiling of `255` bytes and full buffer copying when passed by value — chapter 09 (`09-strings.md`));
  - **6-byte software `Real48`** for machines without a coprocessor, and hardware 80-bit `Extended` and 64-bit integer `Comp` for x87 (chapter 07 (`07-reals.md`));
  - **`set of` bitsets** with a fixed width of up to `256` elements (`32` bytes — chapter 11 (`11-sets.md`)) and flat `record` records with variant field overlays `case .. of`;
  - **stack-based `object` (`TP 5.5`):** a polymorphic value structure whose hidden VMT pointer lies inside the instance itself and must be initialized manually by calling `constructor`, along with 1-word procedural pointers and segmented-memory facilities `near`/`far`, `Mem`/`Port`, `inline($...)`.
- **Why stratum I reached its limit:** passing or assigning an `object` descendant to a base-type variable by value caused physical **object slicing**, cutting off the descendant's fields; the absence of a common hierarchy root and metadata prevented building a visual Windows component environment and form streaming, while the `255`-character limit blocked work with real texts.



### Stratum II. The classic RAD era, heap VMT, and COM (`Delphi 1–7`, `1995–2002`)

- **The era's initial constraint:** the move to event-driven Windows GUIs, component-based `.dfm` form construction, and binary interaction between system modules required reference polymorphism without slicing, long strings, and cross-language contracts.
- **The physical and grammatical response:**
  - **splitting the old `object` into value-based `record` and heap-based `class(TObject)`:** a class variable became a 1-word heap pointer; `TObject.InitInstance` guarantees zeroing memory before entering the constructor; a bidirectional table with negative offsets grew around the VMT pointer (RTTI, class name, `InstanceSize`, parent), type `class of` made a metaclass a first-class value with virtual constructors, and the `published` section under `{$M+}` provided the basis for `.dfm` serialization (chapters 24–28 (`24-classes.md`));
  - **2-word method pointer `TMethod` (`of object` = `Code + Data`):** linked a handler's code address to a particular receiver `Self` without owning the object's lifetime (chapter 22 (`22-callables.md`));
  - **heap-based `AnsiString` (Delphi 2):** a negative-offset header with reference count `refCount` and length + *copy-on-write* semantics (`UniqueString`) removed the `255`-byte barrier while preserving the illusion of a value type;
  - **dynamic array `array of T` (Delphi 4):** the same negative-offset header with `refCount` and a heap length, but **without *copy-on-write*** — writing to `B[0]` after `B := A` changes the shared buffer (the main source of false analogies with strings, chapter 10 (`10-arrays.md`));
  - **`Variant` / `OleVariant` and COM interfaces `IInterface` (Delphi 3):** automatic reference counting through `_AddRef`/`_Release`, interface method tables (IMT) at offsets inside the object, and `ADJUSTOR` thunks that shift the interface pointer back to the beginning of `TObject` (chapter 29 (`29-interfaces.md`)).
- **Why stratum II reached its limit:** single-byte `AnsiString` depended on the Windows system code page and lost characters between locales; collections such as `TList` were built on untyped `Pointer` values; 2-word `TMethod` could not capture local variables of the calling procedure; classic RTTI saw only the `published` section, and manual `Create`/`Free` of classes required `try..finally` discipline.

### Stratum III. Unicode, monomorphized Generics, closures, and extended RTTI (`Delphi 2005–2010`)

- **The era's initial constraint:** software globalization, a need for strongly typed containers at native speed, asynchronous callbacks with context capture, and universal reflection.
- **The physical and grammatical response:**
  - **the `string -> UnicodeString` transition (UTF-16LE, Delphi 2009):** extending the string header with `codePage` and `elemSize` fields (`12` bytes on `Win32`, `16` bytes on `Win64`), literals in the constant segment with `refCount = -1`, code-page-specific `AnsiString(CP)`, and transport type `RawByteString` ([String Types](https://docwiki.embarcadero.com/RADStudio/Florence/en/String_Types_(Delphi)));
  - **`Generics<T>` monomorphization** (following the preparatory step of `advanced record` with methods and `class operator` in 2006): for each closed specialization (`TMonoBox<Integer>`, `TMonoBox<string>`), the compiler generates **separate machine code, its own VMT, and independent `class var` fields** — the direct opposite of Java's *type erasure* ([Declaring Generics](https://docwiki.embarcadero.com/RADStudio/Florence/en/Declaring_Generics), chapter 31 (`31-generics.md`));
  - **anonymous methods `reference to`:** because a procedure's stack is destroyed on return, the compiler lowers a closure into a hidden heap object with a COM-interface reference count and moves captured local *variables* (rather than copies of them!) into a shared heap capture frame ([Anonymous Methods](https://docwiki.embarcadero.com/RADStudio/Florence/en/Anonymous_Methods_in_Delphi), chapter 23 (`23-closures.md`));
  - **extended RTTI (`System.Rtti`, Delphi 2010):** universal container `TValue`, custom attributes `[CustomAttribute]`, control of table emission through `{$RTTI EXPLICIT}` (chapter 36 (`36-rtti.md`)), and direct recovery of an instance through `Intf as TObject`.
- **Why stratum III reached its limit:** the entire binary foundation was still designed around 32-bit `Win32` (`SizeOf(Pointer) = 4`, 10-byte x87 `Extended`, stack exception chain `FS:[0]`), creating a barrier to moving onto 64-bit servers and mobile ARM processors.

### Stratum IV. Multi-target ABI and the architectural lesson of mobile ARC (`XE2–10.3`)

- **The era's initial constraint:** porting the language to `Win64`, `macOS`, `iOS`, `Android`, and `Linux64` with different register conventions, address widths, and hardware stack-unwinding rules.
- **The physical and grammatical response:**
  - introducing `Unit Scope Names` (`System.SysUtils`), pointer-width types `NativeInt`/`NativeUInt`, moving to `SizeOf(Pointer) = 8`, expanding **`TMethod` (`8 -> 16` bytes)** and **`TVarData` (`16 -> 24` bytes)**, platform-dependent splitting of **`Extended`** (`10` bytes on `Win32`, `8`-byte `Double` on `Win64`/`ARM`, `16` bytes on `Linux64` — chapter 70 (`70-floating-profiles.md`)), and replacing `FS:[0]` stack frames with table-based **`PC-Mapped` exception unwinding** ([PC-Mapped Exceptions](https://docwiki.embarcadero.com/RADStudio/Florence/en/PC-Mapped_Exceptions));
  - attempting to adopt the mobile memory model in **`XE4–10.3` through ARC for `TObject`** on iOS/Android/Linux: each object acquired `FRefCount`, breaking cycles required `[Weak]` (zeroed through a global registry) or `[Unsafe]`, and forced resource cleanup used `DisposeOf`, putting the object into a partially destroyed *zombie state*.
- **Why stratum IV caused a reversal:** living with two incompatible memory models for the same `class` (`Free` on Windows versus ARC and `DisposeOf` on mobile targets) split libraries' common source code and undermined destructor predictability.

### Stratum V. Memory unification and deterministic stack-based RAII (`10.3 Rio – 10.4 Sydney`)

- **The era's initial constraint:** the desktop/mobile split had to be removed while giving the language lightweight deterministic RAII without heap allocations or cumbersome cascades of `try..finally`.
- **The physical and grammatical response:**
  - **block-local `var` declarations (`10.3 Rio`):** the *inline variable declaration* mechanism (written as `var X := ...` or `for var I := ...` **without** the word `inline` in code!) narrowed the scope and lifetime of managed variables to a specific `begin..end` block or a single loop iteration ([Inline Variable Declaration](https://docwiki.embarcadero.com/RADStudio/Florence/en/Inline_Variable_Declaration));
  - **unification of the class model (`10.4 Sydney`):** removing ARC from `TObject` on all platforms (the same classic ownership through `Free` / `Owner` everywhere), while retaining reference counting and `[weak]`/`[unsafe]` attributes for interfaces ([Memory Management](https://docwiki.embarcadero.com/RADStudio/Florence/en/Memory_Management));
  - **Custom Managed Records (`10.4 Sydney`):** operators `class operator Initialize`, `Finalize`, `Assign`, and `const [ref]` parameter passing brought automatic deterministic RAII directly onto the stack and into arrays — with a fundamental failure asymmetry: an exception inside `TObject.Create` automatically calls `Destroy`, whereas an exception inside `CMR.Initialize` **does not call `Finalize`** ([Custom Managed Records](https://docwiki.embarcadero.com/RADStudio/Florence/en/Custom_Managed_Records), chapter 13 (`13-managed-records.md`), chapter 68 (`68-lifetime-boundaries.md`)).

### Stratum VI. Hardware realism of FP masks and semantic precision (`11 Alexandria – 13 Florence`)

- **The era's initial constraint:** unmasked FPU exceptions conflicting with external C/C++/SIMD libraries, inconvenient multiline templates, excessive temporary variables in branching, and fragile string literals during refactoring and local directive switching.
- **The physical and grammatical response:**
  - **`11 Alexandria`:** binary literals `%` and digit separators `_` for self-documenting bit masks;
  - **`12 Athens`:** enabling all six FP-exception masks by default in the RTL (`SetExceptionMask`, returning IEEE values `+Infinity`/`NaN` instead of a failing `EZeroDivide` — [12 Athens Release 3](https://docwiki.embarcadero.com/RADStudio/Florence/en/12_Athens_-_Release_3), chapter 70 (`70-floating-profiles.md`)), and multiline literals `'''` with the TEXTBLOCK (`../directives/textblock.md`) line-ending profile;
  - **`13 Florence` (`CompilerVersion = 37.0`):** lazy conditional expression `if..then..else` (evaluating only the selected branch), operators `is not` and `not in` ([Conditional Operators](https://docwiki.embarcadero.com/RADStudio/Florence/en/Conditional_Operators_(Delphi))), directive `noreturn` in the control-flow graph to prevent spurious `W1035` (chapter 20 (`20-routines.md`)), expression `NameOf(...)` resolved at the symbol-table phase before analysis of unused assignments `H2077` (chapter 67 (`67-nameof.md`)), concise CMR operator syntax with **implicit `Self`** (`class operator Initialize;` / `Finalize;`), strict generic constraints `: interface` and `: unmanaged` (the latter rejecting any managed fields and CMR with `E2668` — chapter 32 (`32-constraints.md`)), full option-stack restoration `{$PUSHOPT}`/`{$POPOPT}`, and long `{$IFOPT}` predicates ([What's New (Florence)](https://docwiki.embarcadero.com/RADStudio/Florence/en/What%27s_New)).

## 3. Five engineering rules at the junctions between eras

Where mechanisms from different generations meet in a single line or structure, strict physical boundaries apply:

1. **`ShortString` versus `UnicodeString` and `{$H-}`:** `ShortString` remains a single-byte `1 + N` buffer on the stack, whereas unqualified `string` in the tested `Delphi 13 CE` profiles remained UTF-16LE `UnicodeString` even under `{$H-}` (chapter 09 (`09-strings.md`)).
2. **Four structure models (`object` vs `record` vs `CMR` vs `class`):** `object` is copied by value with a hidden VMT pointer and loses descendant fields when sliced; an ordinary `record` is trivial or automatically managed by its fields; `CMR` adds custom `Initialize`/`Finalize`/`Assign` without a VMT and **without calling `Finalize` on an exception inside `Initialize`**; `class` always lives on the heap and calls `Destroy` on an exception in `Create`.
3. **`TMethod` (`of object`) versus `reference to`:** `TMethod` (`8` or `16` bytes) does not keep an object from being destroyed, whereas `reference to` retains a heap COM frame through reference counting and shares captured local *variables* among all copies of the closure (chapter 23 (`23-closures.md`)).
4. **`: record` versus `: unmanaged` in generics:** the old `: record` constraint admits records with strings and CMR, whereas the new `Delphi 13` `: unmanaged` constraint requires pure bitwise triviality and rejects managed records with code `E2668` (chapter 32 (`32-constraints.md`)).
5. **Stratum I's 256-element foundation inside stratum VI's `not in` operator:** the new `X not in [...]` operator (`Delphi 13`) is built on the classic `set of` set constructor (`0..255`, `32` bytes). For narrow enumerations and small integers (`0..255`), it expands into a fast bit check, but values outside `0..255` exceed the physical limit of a Pascal set (chapter 11 (`11-sets.md`), chapter 17 (`17-expressions.md`)).

# EXTENDEDCOMPATIBILITY — the Extended compatibility representation

**Syntax:** `{$EXTENDEDCOMPATIBILITY ON}` or `{$EXTENDEDCOMPATIBILITY OFF}`.

**Default in the cited source:** `OFF`.

**Documented scope:** Local (applies to subsequent declarations of types and data involving `Extended`).

The directive controls the **binary storage size** of [`System.Extended`](https://docwiki.embarcadero.com/Libraries/Florence/en/System.Extended) on platforms where `Extended` is compressed by default to 8-byte IEEE-754 `Double` (`Win64` SSE2 and `ARM`; see [Multi-Device Considerations](https://docwiki.embarcadero.com/RADStudio/Florence/en/Delphi_Considerations_for_Multi-Device_Applications); on `Win32` x87, `Extended` is always 10 bytes, and on `Linux64` under the System V ABI, 16 bytes; chapter 07 (`../chapters/07-reals.md`), chapter 70 (`../chapters/70-floating-profiles.md`)):
- under **`OFF`**, on `Win64`, `Extended` occupies `8` bytes (`Double`);
- under **`ON`**, on `Win64`, the compiler allocates **10 bytes** (the [`TExtended80Rec`](https://docwiki.embarcadero.com/Libraries/Florence/en/System.TExtended80Rec) layout), **but does NOT enable 80-bit x87 arithmetic**: computation uses the 53-bit precision of `Double`!

```pascal
{$EXTENDEDCOMPATIBILITY ON}
// Win32: SizeOf(Extended)=10, prec64=TRUE, round-trip TExtended80Rec=TRUE
// Win64: SizeOf(Extended)=10, но prec64=FALSE (SSE2) и round-trip TExtended80Rec=FALSE!
```

*English glosses of the retained source comments:*
- Win64: SizeOf(Extended)=10, but prec64=FALSE (SSE2) and round-trip through TExtended80Rec=FALSE!



**Live measurements (`Delphi 13 CE 37.0.60542.8024`, 0.11 pass (`../research/COMPILER_PASS_011.md`), and `P13`):**

| Probe / mode | `SizeOf` | `Unpacked` / `Packed` `(Byte, Extended, Byte)` | `prec64` (`1+1e-17<>1`) and round-trip |
|---|---|---|---|
| `OFF` `Win32` (example 50 (`../../../examples/README.md`), `P13_ExtPrecision_Off32`) | `10` | `24 (E:8,B:18)` / `12 (E:1,B:11)` | `prec64=TRUE`, `rt_eq=TRUE` |
| `OFF` `Win64` (`P13_ExtPrecision_Off64`) | `8` | `24 (E:8,B:16)` / `10 (E:1,B:9)` | `prec64=FALSE`, `rt_eq=TRUE` (`8B`) |
| **`ON` `Win32`** (`P13_ExtCompat_Prec_On32`) | `10` | `24 (E:8,B:18)` / `12 (E:1,B:11)` | `prec64=TRUE`, `rt_eq=TRUE` |
| **`ON` `Win64`** (`P2_ExtCompat_On64`, `P13_ExtCompat_Prec_On64`) | **`10`** | **`24 (E:8,B:18)` / `12 (E:1,B:11)`** | **`prec64=FALSE`, `rt_eq=FALSE`** |

**A false analogy:** unlike C `long double` on Linux x86-64, on `Win64` conversion through `Double` loses low mantissa bits (`EXTENDED_TARGET_PROFILE` = `OPEN` for non-Windows targets).

Source: [Embarcadero](https://docwiki.embarcadero.com/RADStudio/Florence/en/Extended_type_compatibility_(Delphi)). Read on 18.11.2026.

Status: cross-checked against the documentation; sizes, field offsets, `prec64=FALSE`, and `rt_eq=FALSE` under `ON` on `Win64` were measured in example 50 (`../../../examples/README.md`), `P2_ExtCompat_*`, and `P13_ExtCompat_Prec_*`.

## Verification 1.3.0: refined boundaries

**EXTENDED_TARGET_PROFILE — PARTIALLY_RESOLVED.** On ARM32/64, compile-time SizeOf: OFF=8, ON=10, packed record=12, ordinary record=24. This is storage size, not computational precision. DLL producers/consumers with ON/OFF were added on Win32/64, with matching types and a separate lifetime before FreeLibrary.

Scope: Windows DLL probes and compile-only ARM layout; the previous Windows precision/round-trip observations are preserved. Remainder: ARM precision/rounding/runtime ABI requires an Android device or a configured emulator with a harness; Linux/macOS requires the corresponding licensed Delphi compiler, SDK/PAServer, and receiving runtime. Other ABI signatures require a separate producer/consumer rather than SizeOf.

# INLINE — inlineability and the call site

**Syntax:** directive `{$INLINE ON}` / `{$INLINE OFF}` / `{$INLINE AUTO}`; the word `inline;` in a routine header is part of its declaration.

**Default in the cited source:** A conflict between layers (`INLINE_DEFAULT_PROFILE` (`../SOURCE_ISSUES.md#issue-inline-default-profile`), `OPEN`): the *Language Guide* specifies `ON`, while *Compiling* specifies `off` for the IDE (set the mode explicitly).

**Scope according to the documentation:** Two-sided — the state at the **definition point** and at **each call site** is considered.

The `inline` mechanism (since **Delphi 2005**) operates on typed IR inside `.dcu` (chapter 72 (`../chapters/72-inline-semantics.md`)):
- **`ON`:** marks a routine with `inline;` in `.dcu` and expands its body instead of `call`/`ret` at the call site;
- **`OFF`:** suppresses marking or substitution on the corresponding side;
- **`AUTO`:** considers small unmarked routines for inlining (up to **32 bytes** of code according to the help).

```pascal
{$INLINE ON}
function MagicAdd(N: Integer): Integer; inline;
begin
  Result := N + $13572468;
end;
```

**Physical machine-code measurements (`P13_Inline_*`, `Delphi 13 CE` `Win32`):**
Counting constant `$13572468` (`m1`, 3 calls to `MagicAdd; inline;`) and `$24681357` (`m2`, 1 call to ordinary `PlainAdd`) in PE-image sections `.text` / `.itext`:
- **`P13_IfOpt_INLINE` / `P13_Inline_IfOpt_Rel`:** `{$IFOPT INLINE ON}` returned **`ON`** in both IDE templates (`Debug` and `Release`);
- **`P13_Inline_Default_Dbg` / `_Rel`:** `.text: m1=0, m2=1`; **`.itext: m1=3, m2=0`** (all 3 calls physically expanded in `.itext` in both `Debug` and `Release`!);
- **`P13_Inline_DefOn_CallOff` and `P13_Inline_DefOff_CallOn`:** **`.text: m1=1, m2=1`; `.itext: 0`** (`{$INLINE OFF}` on *either* side cancels substitution);
- **`P13_Inline_DefAuto_CallOn`:** `.text: m1=0, m2=1`; `.itext: m1=3, m2=0` (`PlainAdd` without `inline;` **is NOT automatically inlined across units**!).

**Limitations:** changing an `inline` body requires a full rebuild (`Build`) of dependent `.dcu` files; `virtual`/`asm`/open arrays/`.bpl` boundaries are not inlined; missing units in `uses` produce `H2443`. Do not confuse this with C++ ODR, `.dfm` `inline`, or TP `inline($8B/...)`.

Source: [Embarcadero](https://docwiki.embarcadero.com/RADStudio/Florence/en/Calling_Procedures_and_Functions). Read on 18.11.2026.

Status: checked against the documentation; result preservation (example 49 (`../../../examples/README.md`)) and physical substitution/cancellation in `.itext` measured in `P13_Inline_*` on `Win32 Debug/Release`.

## Verification 1.3.0: refined boundaries

**INLINE_DEFAULT_PROFILE — RESOLVED_SELECTED_PROFILE.** Without an explicit switch, IFOPT INLINE ON is true in both Windows Debug/Release configurations. With O+, the new ON/AUTO/OFF and marked/plain forms produce the same computed result; this alone does not prove inlining; the earlier physical marker/count probes across units remain. This is a recommendation to the compiler, rather than a guarantee that every call will be inlined.

Scope: The effective current default and finite within-unit/cross-unit controls on Win32/Win64. Remainder: A precise decision about another call requires its source, profile, and machine code. The optimizer's algorithm across releases has not been reconstructed and is not required as an invented language rule.

# PUSHOPT / POPOPT — saving and restoring options

**Syntax:** `{$PUSHOPT} ... {$POPOPT}`.

**Default in the specified source:** Compiler option-stack commands; they have no ON/OFF default of their own.

**Documented scope:** `Local` (a LIFO stack within the current unit).

## The option-stack mechanism and findings from series `P2`–`P3` (`0.11`)

The directives were introduced in **Delphi 13 Florence** to change switches (`{$R-}`, `{$Q-}`, `{$J+}`, `{$O-}`, `{$WARNINGS ...}`) locally and restore the original profile exactly without cumbersome `{$IFOPT}` tests (example 29 (`../../../examples/README.md`), `0.8`: `on`, `off`, `on`; chapter 41 (`../chapters/41-directives.md`), chapter 59 (`../chapters/59-directive-profiles.md`)). Nested pairs follow LIFO, but **do not** preserve `{$DEFINE}`/`{$UNDEF}` symbols, the `.inc` stream, or variable state.

The original comment “ВЕСЬ стек опций целиком” below is imprecise: `POPOPT` restores the top snapshot; lower snapshots remain on the stack. The original source is retained to match the compiler evidence.

```pascal
// Проверено в P2_PushOpt_Sel_Effect и P3_PushOpt_Discriminate (Delphi 13 CE 37.0)
{$PUSHOPT RANGECHECKS} // хвостовой аргумент не сужает снимок!
  {$R-}{$Q+}
{$POPOPT} // восстанавливает ВЕСЬ стек опций целиком: after_pop R=ON, Q=OFF
```

*English glosses of the retained source comments:*
- Verified in P2_PushOpt_Sel_Effect and P3_PushOpt_Discriminate (Delphi 13 CE 37.0)
- the trailing argument does not narrow the snapshot!
- restores the option states from the top saved snapshot: after_pop R=ON, Q=OFF



Live experiments in **series `P2` and `P3`** (COMPILER_PASS_011 (`../research/COMPILER_PASS_011.md`)) revealed two critical boundaries:
1. **Complete rollback rather than selective rollback (`PUSHOPT_TABLE_TYPOS`, status `OPEN`):** despite mentions of named arguments and typos `IMPOTEDDATA` / `FINITEFLOATT` in the *Option OPT* table, calling `{$POPOPT}` in probes `P2_PushOpt_Sel_Effect` and `P3_PushOpt_Discriminate` rolled back **all changed options (`R=ON; Q=OFF`)**.
2. **Silent ignoring of typos:** probes `P3_PushOpt_Bogus` (`BOGUS_OPT`), `P3_PushOpt_Typo1` (`FINITEFLOATT`), and `P3_PushOpt_Typo2` (`IMPOTEDDATA`) compiled with **`0` diagnostics** (unlike `{$IFOPT}`, where typos immediately caused `E1030`). Seven rare table names are examined separately in `EXTRA_DIRECTIVES_NOT_REVIEWED` (`../SOURCE_ISSUES.md#issue-extra-directives-not-reviewed`) (EXTRA_OPTIONS.md (`../research/EXTRA_OPTIONS.md`)).

## Protection against false analogies

Unlike MSVC `#pragma warning(push/pop)`, which saves only warnings, `{$PUSHOPT}` also captures code-generation checks; unlike Free Pascal `{$PUSH}`/`{$POP}`, Delphi 13 strictly uses `{$PUSHOPT}`/`{$POPOPT}` — write them **without arguments** (SOURCE_ISSUES (`../SOURCE_ISSUES.md#issue-pushopt-table-typos`)).

Source: [Embarcadero](https://docwiki.embarcadero.com/RADStudio/Florence/en/Option_OPT_(Delphi)). Read on 18.11.2026.

Status: complete stack rollback and ignored trailing names are confirmed in `0.8` and `P2`–`P3` (`Delphi 13 CE`); `PUSHOPT_TABLE_TYPOS` remains `OPEN`.

## Verification 1.3.0: refined boundaries

**PUSHOPT_TABLE_TYPOS — PARTIALLY_RESOLVED.** A nested include restores R/Q through the stack. An unmatched PUSHOPT produces W1079, and POPOPT W1078, on Win32/64. The previous BOGUS_OPT/FINITEFLOATT trailing portions were accepted, but the entire set was restored, so this does not prove a selective subset.

Scope: A nested stack, include, and imbalance in the current Windows profile. Remainder: A selective subset requires an official exact grammar/correction to Option OPT, or an Embarcadero example with distinguishable partial restoration and a version-matched compiler. Acceptance of an ignored trailing portion is not an answer.

# WARN — a specific warning class

**Syntax:** `{$WARN identifier ON|OFF|ERROR|DEFAULT}`.

**Default in the cited source:** the page refers to enabled warnings; actual project values are determined separately.

**Scope according to the documentation:** `Local`, from the directive's position in the text.

## Selective filtering versus `{$WARNINGS}` and the `DEFAULT` pitfall

Unlike routine-scoped `{$WARNINGS}` (`warnings.md`), `{$WARN}` configures **one specific warning class** by its canonical ID (`SYMBOL_DEPRECATED`, `COMPARING_SIGNED_UNSIGNED`, `HIDDEN_VIRTUAL`, `IMPLICIT_STRING_CAST`, etc.; the complete catalog of **`76` IDs verified in `Delphi 13 CE`** is given in chapter 41 (`../chapters/41-directives.md`), and profiles in chapter 59 (`../chapters/59-directive-profiles.md`)):
- **`ON` / `OFF`** enables or suppresses the warning further down the text;
- **`ERROR`** promotes an occurrence of this class from `Wxxxx` to compilation error `Exxxx`;
- **`DEFAULT`** restores the ID's state from **Project Options (`.dproj` / CLI)**, rather than reverting to the preceding local `{$WARN}` in the file; for exact local restoration in Delphi 13, use `{$PUSHOPT}` / `{$POPOPT}` (`pushopt-popopt.md`).

## `P12` / `P15` contrasts and a false analogy with MSVC

```pascal
// Проверено в P12_Warn_Granular32 / P12_Warn_Error32 (Delphi 13 CE, Win32 Debug)
{$PUSHOPT}
{$WARN SYMBOL_DEPRECATED OFF}
LegacyProc; // предупреждение W1000 подавлено (diags=[], stdout='legacy')
{$POPOPT}
// При {$WARN SYMBOL_DEPRECATED ERROR} -> отказ: E1000 Symbol 'LegacyProc' is deprecated
```

*English glosses of the retained source comments:*
- Tested in P12_Warn_Granular32 / P12_Warn_Error32 (Delphi 13 CE, Win32 Debug)
- warning W1000 is suppressed (diags=[], stdout='legacy')
- With {$WARN SYMBOL_DEPRECATED ERROR} -> rejection: E1000 Symbol 'LegacyProc' is deprecated



- **Series `P12` (`Win32 Debug`):** `OFF` in `P12_Warn_Granular32` suppressed `W1000` (`diags=[]`, `run_exit = 0`); `ERROR` in `P12_Warn_Error32` stopped the build with code **`E1000`**.
- **Series `P15` (`Win32 Debug`):** `P15_Warn_Ids_Verified32` accepted **all `76/76`** IDs without `W1030`/`E1030` (`run_exit = 0`); `COMPARING_SIGNED_UNSIGNED ERROR` produced **`E1023`** (`P15_Warn_SignedUnsigned_Err32`); hiding a `virtual` method without `override`/`reintroduce` belongs to **`HIDDEN_VIRTUAL`** (**`W1010`** even under `HIDING_MEMBER ERROR`, **`E1010`** under `HIDDEN_VIRTUAL ERROR`, `0` diagnostics under `OFF`), whereas non-`virtual` `HIDING_MEMBER` produced `0` diagnostics.
- **False analogy (MSVC):** `#pragma warning(default: 4996)` resets the rule to the compiler's factory default, while `{$WARN ... DEFAULT}` retrieves the project's policy.

Source: [Embarcadero](https://docwiki.embarcadero.com/RADStudio/Florence/en/Warning_messages_(Delphi)). Read on 18.11.2026.

Status: `W1000`/`E1000` confirmed in `P12`, and the catalog of `76/76` IDs, `E1023`, and the contrast of `HIDDEN_VIRTUAL` (`W1010`/`E1010`) vs `HIDING_MEMBER` in series `P15` (`Delphi 13 CE`, `Win32 Debug`).
